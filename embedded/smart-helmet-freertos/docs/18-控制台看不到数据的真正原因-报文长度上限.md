# 18 - 「板子在发、订阅者收得到、控制台却没数据」的真正原因：报文长度上限

> 实测日期：2026-09-14
> 结论一句话：**巴法云该主题的"最后一条消息"记录字段只有 191 字节。超过 191 字节的报文，MQTT 转发照做、记录不写——于是订阅者收得完整、设备侧回环确认也成功，唯独控制台永远看不到。**

---

## 一、症状（长什么样）

- 板子 OLED 第 8 行：`NET: OK p=26 e=26`，`p` 和 `e` **同步增长**（说明回环确认也过了）；
- 用 `bemfa_tap.py` 订阅 `temp001`，**能连续收到 seq 递增的板子报文**（说明数据真的过了 Broker）；
- 但巴法云控制台 / HTTP 接口的 `msg`、`time` **纹丝不动**，一直停在更早的一条上。

三条同时成立，看起来自相矛盾。之前一度怀疑"假成功""被别的客户端顶掉"，**都被这一条解释统一推翻了**。

---

## 二、怎么定位的（三个假设，逐个排除）

排查时最忌讳一上来就改代码，先把可能性列全，再用实验逐个杀掉：

| # | 假设 | 怎么验证 | 结果 |
|---|---|---|---|
| 1 | 板子根本没发上去（假成功） | `bemfa_tap.py` 订阅监听，看 seq 是否递增 | **排除**：收到多条 seq 递增报文，迟到若干秒才到（是实时转发，不是保留副本） |
| 2 | 短时间只记录前几条（限流） | 连发 **8 条极短报文**（长度不变、只改 seq） | **排除**：8 条全部被记录 |
| 3 | 报文太长，记录写不进去 | **长度阶梯**：依次发 20 / 159 / 160 / 180 / 185 / 190 / 191 / 192 / 195 / 200 / 220 / 240 / 250 / 255 / 400 / 800 字节，每发一条立刻回查云端记录 | **命中** ✅ |

### 长度阶梯实测结果

| 报文长度 | 是否写进云端记录 |
|---|---|
| 20 B | ✓ |
| 159 / 160 B | ✓ |
| 180 / 185 B | ✓ |
| 190 B | ✓ |
| **191 B** | **✓（上限）** |
| 192 B | ✗ |
| 195 / 200 / 220 / 240 / 250 / 255 / 400 / 800 B | ✗（记录停在 191 B 那条） |

**阈值正好是 191。**

## 三、为什么是 191

191 = 767 ÷ 4。MySQL 的 InnoDB 索引前缀长度上限是 767 字节；用 utf8mb4（每字符最多 4 字节）建索引时，字符串列最多只能取前 **191** 个字符。所以这个 `VARCHAR(191)` 不是随便取的，它是"能被索引的最长字符串"。

平台这边的行为是：**写入失败就整条丢弃**（而不是截断），但消息转发走的是另一条路径，不受影响。这就造成了"收得到、看不到"。

> 注意区分：**转发**（broker → 订阅者）和**记录**（broker → 平台数据库 → 控制台/HTTP 接口）是两回事。
> 之前一直拿 `msg`/`time` 当"设备有没有在发"的判据，就是把这两件事混为一谈了。

---

## 四、修复

### 4.1 把上报报文压到 191 字节以内

固件原本的 JSON 有 **20 个字段、约 250 字节**，必然被丢。现改为**紧凑键名**，典型值 **147 字节**、最坏值 **170 字节**：

```json
{"ts":"10:49:24","seq":1234,"hr":114,"spo2":null,"t":26.3,"h":57.0,
 "gas":16,"ax":-1.2,"ay":0.0,"az":9.8,"st":"normal",
 "up":12345678,"tsv":0}
```

**字段映射（紧凑 → 原义）**

| 紧凑键 | 原义 | 紧凑键 | 原义 |
|---|---|---|---|
| `ts` | 时间 `HH:MM:SS` | `ax/ay/az` | 三轴加速度 |
| `seq` | 报文序号 | `st` | 状态（`normal` / 报警文案） |
| `hr` | 心率 bpm | `up` | 上电后运行毫秒数 |
| `spo2` | 血氧 % | `tsv` | 时间戳是否可信（1=可信） |
| `t` / `h` | 温度 ℃ / 湿度 % | `gas` | 气体 ADC 原始值 |

> 🔻 **后续修订（2026-09-22，见 `docs/39`）**：`lux` 字段已随光照功能整体删除；
> 典型报文约 161 字节，最坏 190 字节（余量仅 1 字节，已回到 191 字节上限以内）。
> 本文讲的"191 字节上限"及其判据**仍然完全有效**。

两处细节：
- **时间只留 `HH:MM:SS`**：完整 ISO 串要 20 字节，省下的 12 字节很值；精确日期以云端记录的接收时间为准。
- **`"seq":N,` 必须保留带尾逗号的形式**：回环确认就靠这个模式在接收缓冲里定位自己刚发的那一条。

### 4.2 再加一道长度兜底

`enforce_payload_limit()`：发之前检查长度，超过 `NET_PAYLOAD_MAX`(180B) 就退化成最小报文 `{"seq":N,"ovf":1}`。
**宁可少报几个字段，也不能整条丢**；触发时串口会留一行 `[NET] WARN payload ...`，便于发现是哪个字段把报文顶超了。

### 4.3 调试日志带上长度

`[NET] published 147B: {...}` —— 长度本身就是一条证据，以后一眼就能看出有没有越线。

### 4.4 开关

`user_config.h`：

```c
#define NET_JSON_COMPACT      1     /* 1 = 紧凑键名(≈150B, 能被云端记录) */
#define NET_PAYLOAD_MAX       180   /* 报文长度硬上限, 超出则退化为最小报文 */
```

只有在**只给本机上位机消费、不在乎云控制台**时，才把 `NET_JSON_COMPACT` 置 0 换回完整字段。

## 五、验证（烧录前就已证明）

`tools/bemfa_compact_payload_check.py` 用固件的**真实紧凑格式**在电脑上实发三条并回查：

| 报文 | 长度 | 云端是否记录 |
|---|---|---|
| 典型值（心率/温湿度都有） | 147 B | ✓ 记录的就是这一条 |
| 最坏值（各字段都取最大位数） | 170 B | ✓ |
| 无数据（null 兜底） | 146 B | ✓ |

三种都远在 191 以内，且**全部被云端记录** ⇒ 烧录新固件后，板子数据会正常出现在控制台上。

## 六、以后加字段要注意

1. **加字段前先算长度**：`NET_PAYLOAD_MAX`(180B) 是红线，`enforce_payload_limit()` 是保险，但触发保险就意味着丢字段。
2. **想报更多数据怎么办**：在巴法云**再建一个主题**（如 `temp002`），把次要数据发到那个主题——每条主题各自独立记录、各自 191 字节上限。
3. **判据别再用 `msg`/`time` 单打独斗**：
   - 判断"设备在不在发" → `bemfa_tap.py`（看 seq 是否递增）或 OLED 的 `e` 计数；
   - `online`/`pubOnline` 有 1~2 分钟滞后，不能做实时判断。

## 八、一句话总结

> **控制台看不到数据，未必是链路问题。**
> 先量一下报文的字节数：**过 191 就只会被转发、不会被记录**。
> 判"发没发出去"看 `seq`/`e`，判"能不能被看到"看**长度**。
