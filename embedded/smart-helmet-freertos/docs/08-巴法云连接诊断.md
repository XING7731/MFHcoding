# 08 - 巴法云连接诊断（联网不稳定 / 连不上云端）

> 本文针对的现象：**WiFi 看起来连上了，但云端看不到设备；或者连上之后反复掉线重连。**
>
> 这份文档配合固件新增的**日志与自检模式**使用。核心思路是：**不再猜，让固件把病因说出来。**

---

## 一、先记住三件事

| # | 结论 | 说明 |
|---|---|---|
| 1 | **主题必须建在"MQTT 控制台"** | 巴法云的 TCP（创客云，`bemfa.com:8344`）和 MQTT（`bemfa.com:9501`）是**两套接入**，建主题的入口不同。本工程走 MQTT，主题要在 <https://cloud.bemfa.com/mdevice.php> 确认存在。**旧工程 `stm32-dht11-cloud` 用的 `temp001` 是按 TCP 创客云的习惯建的**——它是"连不上云端"的第一嫌疑。 |
| 2 | **同一私钥只允许一个连接** | 旧工程如果还通着电跑着，用的是**同一个私钥**，两边会**互相把对方踢下线**，现象正是"断了又连、连了又断"。 |
| 3 | **ESP01S 必须独立 3.3V 供电** | 发射瞬间电流可达 ~300mA。从开发板取电会瞬时压降导致模块**重启**，表现为"连上一会儿就断"。固件现在能直接把这件事测出来（见下面 `resets=`）。 |

---

## 二、最快的一步：让固件只跑网络

把 `user/Inc/user_config.h` 改成：

```c
#define NET_SELF_TEST      1     /* 只跑联网流程, 不启动传感器/OLED/报警 */
#define NET_AT_LOG_ENABLE  1     /* 把 AT 收发全过程打到调试串口 */
```

重新编译烧录。此时固件**只做一件事**：反复执行

```
AT → 连 AP → 建 TCP → MQTT CONNECT → 发一条测试报文
```

并把每一步的原始 AT 交互打印到 **USART2（PA2=TX / PA3=RX，115200-8N1）**。

**为什么值得这么做**：它排除了 DHT11/DS18B20 周期性关闭中断等干扰，日志不会被别的任务淹没，得到的是一条干净的"网络病历"。

排完问题后把 `NET_SELF_TEST` 改回 `0`。

---

## 三、读日志：判据表

日志长这样（`[AT]` 后面是模块的原话，`[TEST]`/`[NET]` 是固件的判断）：

```
[AT] AT
[AT] OK
[AT] ATE0
[AT] OK
[AT] AT+CWMODE=1
[AT] OK
[AT] AT+CWJAP="0001","****"
[AT] WIFI CONNECTED
[AT] WIFI GOT IP
[AT] OK
[AT] AT+CIPSTART="TCP","bemfa.com",9501
[AT] CONNECT
[AT] OK
[TEST] publish OK
```

### 3.1 卡在 AT 握手（`AT check failed code=1`）

| 日志特征 | 病因 | 处置 |
|---|---|---|
| 发 `AT` **一句应答都没有**（`resp=(no response)`） | 波特率不对 / 接线反了 / 供电不足 | ① 试 9600（改 `main.c` 的 `MX_USART1_UART_Init`）；② 确认 **ESP TX → PA10**、**ESP RX → PA9**（交叉）；③ 换独立 3.3V 供电 |
| 收到一堆乱码（日志里是 `.` 和乱字符） | 波特率不匹配或时钟不对 | 确认板子确实按 8MHz HSE ×9 = 72MHz 运行（`SystemClock_Config`） |
| 偶尔有 OK，但 `resets=` 在涨 | **模块在反复重启 → 供电不足** | 独立 3.3V LDO + 模块 VCC/GND 之间并 100µF 电解 + 0.1µF 瓷片 |

### 3.2 卡在连 AP（`join AP failed`，`step=3`）

| 日志特征 | 病因 | 处置 |
|---|---|---|
| `+CWJAP:...FAIL` 或反复出现 `WIFI DISCONNECT` | 热点不是 2.4GHz / 密码错 / 信号太弱 | 手机热点**必须锁 2.4GHz**（"双频合一"和"5GHz 优先"都不行）；把手机放到板子 1m 内 |
| 一直没响应直到超时 | 模块忙 / 热点拒绝 | 看 `AT+CWJAP?` 的输出；固件已改为**超时后先查实际状态再决定是否断开**，避免自己拆掉好连接 |
| `resp=` 里能看到 `No AP` | 确实没连上 | 同上 |

> **本次已改进**：固件在连 AP 前先发 `AT+CWJAP?` 查询。**如果已经连在同一个 AP 上就直接跳过重连**——以前每次重连都无条件重发 `CWJAP`，会把已经建好的连接先拆掉再重连（耗时数秒，期间 TCP 必断），这是"链路一抖就演变成一次完整断连"的重要放大器。

### 3.3 卡在建 TCP（`tcp connect failed`，`step=4`）

这一步固件会自动做两件诊断：打印 `AT+CIPDOMAIN="bemfa.com"` 的结果，并**自动改用 IP 直连重试一次**。

| 日志特征 | 病因 | 处置 |
|---|---|---|
| `DNS Fail` / `ERROR`，而后面 `AT+CIPDOMAIN` **没有返回 IP** | **手机热点下发的 DNS 不解析外网域名** | 固件已自动改用 `MQTT_BROKER_IP_FALLBACK`（`119.91.109.180`）重试；若仍失败，在电脑上 `nslookup bemfa.com` 把新 IP 填进去 |
| `AT+CIFSR` 显示 `0.0.0.0` | DHCP 没拿到 IP | 热点开了"最多连接设备数"限制或 MAC 过滤；重启热点 |
| `AT+CWJAP?` 显示 `No AP` | 实际根本没连上 AP（代码以为连上了） | 回到 3.2 |
| `ALREADY CONNECTED` | 残留的半死连接 | 固件已在 `CIPSTART` 前先 `CIPCLOSE`，正常不会出现；若仍出现请贴日志 |

### 3.4 卡在 MQTT（`mqtt connect failed`，`step=5`）—— **这一行信息量最大**

固件会打印 `rc=` 和 `connack=0xNN`：

```
[NET] mqtt connect failed rc=2 connack=0x05 (not authorized)
```

| `rc` | `connack` | 含义 | 处置 |
|---|---|---|---|
| 3 | `0xFF` | **完全没收到 CONNACK**（超时或被中间设备掐断） | 与账号无关：查热点/运营商是否拦了 9501 端口；看日志里有没有紧跟的 `CLOSED` |
| 2 | `0x05` | **未授权** → 私钥不对，或主题不在 MQTT 控制台 | ① 核对 `BEMFA_UID`（32 位十六进制）；② **到 MQTT 控制台确认主题存在**；③ 改用"方式二"（见下） |
| 2 | `0x04` | 用户名或密码错 | 说明只有方式一可用时不该走到这；检查是否误填了 `MQTT_USERNAME` |
| 2 | `0x02` | ClientID 被拒 | `BEMFA_UID` 填错了 |
| 2 | `0x01` | 协议版本不支持 | 极少见；确认 broker 是 `bemfa.com:9501`（**不是** 8344） |
| 2 | `0x03` | 服务不可用 | 云端临时故障，稍后再试 |
| — | — | 能看到 CONNACK 成功但**控制台没数据** | 见第五节 |

> **方式二（备用鉴权）**：如果方式一被拒，到巴法云"连接密钥"页面取 `appID` / `secretKey`，填进 `user_config.h`：
> ```c
> #define MQTT_USERNAME   "你的appID"
> #define MQTT_PASSWORD   "你的secretKey"
> ```
> 代码无需改动，`MQTT_Connect()` 会自动按 MQTT 规范带上用户名/密码字段。

### 3.5 `publish failed`（连着但发不出去）

| 日志特征 | 病因 | 处置 |
|---|---|---|
| `SEND FAIL` | 链路拥塞或对端已断 | 固件已做**原地重试 2 次**，并把重连改为**指数退避 5s→60s**，不会再把一次抖动放大成一次完整断连 |
| 马上跟着 `CLOSED` | 服务器主动断开 | 通常是"同一私钥被别处占用"（见第一节第 2 条） |
| `link is not valid` | 模块认为 TCP 已断 | 正常重连流程会处理 |

### 3.6 诊断行的三个数字

正常运行时每次发布后会打印（只在数值变化时出现）：

```
[NET] diag: ovf=0 rstrt=0 err=0 resets=0
```

| 字段 | 正常值 | 在涨说明什么 | 处置 |
|---|---|---|---|
| `ovf` | 0 | 环形缓冲写满丢字节（任务侧消费不及时） | 偶发可接受；持续增长说明串口流量异常 |
| `rstrt` | 0 | 接收链路掉过、被看门狗救回 | 每次都是因为中断被临界区压制导致的溢出错误（ORE），已能自愈；若很频繁可考虑把 USART1 接收改 DMA 循环模式 |
| `err` | 0 | 线路错误（帧错/噪声/溢出）事件数 | 每次都是一个 ORE 现场；持续增长说明 DHT11/DS18B20 的临界区很频繁（正常现象），自愈机制在工作 |
| **`resets`** | 0 | **ESP01S 检测到启动横幅 `ready` = 模块重启过** | **重点看这个**：只要它不为 0 且持续增长，就是**供电不足**，先修电源再谈其它 |

## 四、分层排查顺序（按嫌疑排序）

```
① 硬件供电   ← 最常见。ESP01S 独立 3.3V + 100µF；看 resets= 是否在涨
② 手机热点   ← 必须 2.4GHz；已连设备数限制；把手机放近
③ 网络出口   ← 热点 DNS 是否解析（看 CIPDOMAIN）；IP 直连是否可行
④ 云端账号   ← 私钥正确？主题在 MQTT 控制台？同私钥没被别处占用？
⑤ 代码/串口  ← 看 ovf/rstrt/err 三个计数是否在涨
```

**一条经验**：如果 `resets=0`、`rstrt=0`、`err=0`，但 MQTT 建立后过一阵又断，那问题**几乎不可能在 STM32 代码里**，一定在第 ①②③④ 层——因为这三个计数就是代码层健康的体检指标。

---

## 五、`publish OK` 但控制台看不到数据

这说明**链路完全正常**（TCP 通了、MQTT 认证过了、报文发出去了），问题只在**主题**：

1. 主题名是否与 `BEMFA_TOPIC` 完全一致（区分大小写）；
2. 主题是否建在 **MQTT 控制台** <https://cloud.bemfa.com/mdevice.php>；
3. 控制台页面需要刷新才能看到最新数据；
4. 想"只更新云端数据不推送"可以用 `主题名/up`，想"推送给订阅者"用 `主题名/set`。本工程用的是**裸主题名**（标准的设备上报方式）。

## 七、AT 速查（可在串口助手手工敲，验证硬件）

用 USB-TTL 直接接 ESP01S（**注意 3.3V 电平，别用 5V**），115200，勾选"发送新行"：

```
AT                    → OK
ATE0                  → OK（关回显）
AT+CWMODE=1           → OK
AT+CWJAP?             → +CWJAP:"0001",...,-55   （No AP = 没连上）
AT+CIFSR              → STAIP,"192.168.x.x"     （0.0.0.0 = 没拿到 IP）
AT+CIPDOMAIN="bemfa.com"  → +CIPDOMAIN:119.91.109.180  （无输出 = DNS 不解析）
AT+CIPSTART="TCP","bemfa.com",9501   → CONNECT / OK
AT+CIPCLOSE           → OK
```

**如果手工敲 `AT+CIPSTART` 也连不上，那一定不是 STM32 代码的问题**——这是最有效的"责任划分"实验。
