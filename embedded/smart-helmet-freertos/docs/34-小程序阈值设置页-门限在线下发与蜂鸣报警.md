## 一、先把"消息怎么走到设备"说清楚

这是本轮唯一一个无法在本地测的环节，所以先把它钉死。整条下行分四段：

```
① 小程序  --HTTPS-->  apis.bemfa.com/va/sendMessage
                      ?uid=<私钥>&topic=<主题>/set&type=1&msg=<报文>
             （只需 request 合法域名，与取数是同一台主机、同一份白名单）

② 巴法云   ------>  把消息发布到 "<主题>/set"

③ 设备     ------>  设备上报时已经订阅了裸主题 <主题>（MQTT_SUBSCRIBE_ENABLE），
                     平台这条推送正好落在它已订阅的主题上，
                     因此落进 ESP01S 的 AT 环形接收缓冲（1024 字节）

④ 固件     ------>  WifiTask 每轮（10 秒）调一次 net_poll_config()，
                     在缓冲里认出 "cfg":1 标记 → AlarmCfg_ApplyJson() 解析提交
```

### 1.1 `/set` 这个后缀的语义（已核官方文档 + 本项目实测）

巴法云官方文档《MQTT协议接入》原文：

> **set 指令**　推送消息时：主题名后加 `/set` 推送消息，表示**向所有订阅这个主题的设备们
> 推送消息**，假如推送者自己也订阅了这个主题，消息不会被推送给它自己，以防止自己推送的
> 消息被自己接收。
>
> **up 指令**　推送消息时：主题名后加 `/up` 推送消息，表示**只更新云端数据，不进行任何推送**。

本工程在 2026-09-13 已经实测过这条规则（见 `docs/09`，用 `bemfa_check.py` 走 MQTT 实测）：

```
发布到 temp001      -> 本机收到回环
发布到 temp001/set  -> 未回给自己（符合巴法云文档规定）
发布到 temp001/up   -> 未回给自己（符合巴法云文档规定）
```

### 1.2 ★ 为什么不能直发裸主题

云端的取数接口只给「该主题最新一条」（`num>1` 返回 `data:null`，见 `docs/23`）。
**往裸主题直发会把设备刚上报的那条遥测顶掉**，实时监测页立刻显示成过期数据 ——
为了下发一条配置而破坏正在工作的遥测通道，是明确的负收益。

所以统一发 `<主题>/set`：它进的是另一个主题桶，原主题的记录一动不差。
（这一点在 `tools/wxmp_thresh_test.js` 里被断言锁住：`cmdTopicText` 必须以 `/set` 结尾。）

> 顺手记一条以后会用得上的：`/up` 是"只更新云端不推送"。将来若要"小程序只改云端不惊动设备"，
> 它才是对的工具 —— 现在用不到。

## 二、九个关键设计决定（含被否掉的做法）

### 2.1 门限只放 RAM，不写 Flash ★

**否掉的做法**：把门限写进 Flash，掉电不丢。

**为什么否掉**：写 Flash 要先擦一整页（1KB），擦除期间 CPU 取指会被总线停住
**20~40ms**。本工程有一个 **5ms 周期**的撞击监视任务（`IMPACT_PERIOD_MS`，
是摔倒判据的采样源，见 `docs/28`）。为了"门限掉电保存"去冒"漏掉一次撞击窗口"
的风险，账不划算。

**代价与补偿**：设备每次上电回到出厂默认。补偿不是"让设备记住"，而是
**"让设备随时可被纠正"**：

- 每帧遥测带一个配置指纹 `cv`；
- 小程序拿本机门限算出 cv 与设备回读的比对：
  - 相等 → 设备当前用的就是你设的这套，**不需要设备回发任何应答报文**
  - 不等 → 还没生效（设备离线 / 下发被拒 / 报文没送到），界面上直接说"未同步，请重新下发"

> 为什么不做"设备回发应答"：设备回发的任何消息都会占用云端该主题的
> "最新一条"，把遥测记录顶掉（就是 1.2 节那个坑）。cv 是**搭在已有报文上**的
> 顺风车，成本只有约 11 字节。

### 2.2 cv 指纹：算法刻意选得极简

```
h = 5381
逐值（按 tHi,tLo,hHi,hLo,gas,hrLo,hrHi,sp,buz 顺序）取 int32 小端 4 字节：
  h = ((h * 33) ^ byte) & 0xFFFF
```

**为什么用这么简单的东西**：它要在 **C 和 JS 两侧手写实现**。任何涉及浮点、
字符编码或字节序假设的算法都有"两边算出不同数"的风险，而后果是：
**设备其实生效了，小程序却一直说"没生效"，人会不停地重发。**

交叉验证方式不是"两边各写一遍然后相信它们一样"，而是：
`tools/alarm_cfg_sim.py` 产出对照向量 → `tools/wxmp_thresh_test.js` 逐条复算。
出厂默认门限的指纹是 **38972 (0x983C)**，这个数同时写在 `alarm_cfg.h` 的注释里，
测试会同时断言"JS 算出来是它"和"注释里写的也是它"。

### 2.3 ×10 定点 vs 纯整数：这是真踩过的坑 ★

| 字段 | 量纲 | 写法 |
|---|---|---|
| `tHi` `tLo` `hHi` `hLo` | 摄氏度 / %RH | **×10 定点**，25.5℃ → `255` |
| `gas` `hrLo` `hrHi` `sp` `buz` | 整数 | **纯整数**，`30` 就是 `30` |

固件里对应两个不同的解析函数（`cfg_find_fixed` / `cfg_find_int`）。

**踩坑经过**：最初只有一个"×10"解析函数，于是 `"gas":30` 被读成 `300` →
一读就超量程（气体量程 1~100）→ **每一条下发都被整条拒绝**。现场表现是
"怎么点都没反应"，而且没有任何日志能指向真正原因。

**现在的防护**：
- `alarm_cfg_sim.py` 里有专门断言锁住 `gas=30 必须读成 30`；
- `wxmp_thresh_test.js` 用 **Python 产出的报文原文逐字节对照** `buildConfigMsg`。

> 为什么是"逐字节对照报文"而不是"在 JS 里也写一个解析器再互验"：
> 自己重写一份解析器来验自己生成的报文，等于自证。走"JS 生成 → 与 Python 的
> 参照实现逐字节相同 → Python 那边已验证自己的报文能被自己的规则读回同一组值"
> 这条链，才是真的闭的。

### 2.4 越界一律"整条拒绝"，不逐字段采用 ★

**否掉的做法**：逐字段采用（谁合法就用谁）。

**为什么否掉**：门限之间有约束（高必须严格大于低）。若逐字段采用，一条只写了
`tHi=25`、没写 `tLo` 的报文，会让 `25 < tLo(旧值可能是 30)` 这种组合生效 ——
**那条报警判据当场变成"永远为真"**，蜂鸣器长鸣不停。

所以：候选配置先在本地**整体成型**，校验不过就整条丢掉、原配置一字未动。
固件侧是 `AlarmCfg_ApplyJson`，小程序侧是 `validateThresh()`。

**小程序侧为什么要复制同一套边界**：不是为了"防止乱填"，而是让它在**下发前**
就拦住自己知道会被拒的值。否则用户看到的现象只是"点了没反应"，
完全不知道是被拒了、更不知道差在哪。两侧的边界值由
`alarm_cfg.h` 的 `CFG_*` 宏与 `wxmp_thresh_test.js` 交叉核对，**要求逐项完全相等**：

| 方向 | 后果 | 是否允许 |
|---|---|---|
| 小程序比固件**松** | 放行一个必然被拒的值 → "点了没反应" | ✗ 必须相等 |
| 小程序比固件**紧** | 用户永远调不到固件其实接受的值 | ✗ 必须相等 |

### 2.5 迟滞：不然蜂鸣器会"啾啾" ★

门限附近的值一定在抖（温度 25.0/25.1 来回跳，气体 ADC 本身就有几个 LSB 的噪声）。
没有迟滞时，"报警 → 立刻恢复 → 下一轮又报警"会让蜂鸣器变成一串没完没了的啾啾声，
而现场其实什么都没变。

规则（`app_tasks.c` 的 DataProcTask）：

```
值越过门限            → 置位，开始报警
值回落到 门限 − 迟滞   → 才解除
```

**迟滞只影响"解除"，不影响"触发"** —— 触发永远按用户设的那个数。

| 量 | 迟滞 |
|---|---|
| 温度 | 0.5 ℃ |
| 湿度 | 2.0 %RH |
| 气体 | 3 |
| 心率 | 2 bpm |
| 血氧 | 1 % |

常量在 `alarm_cfg.h`，界面上也写出来了（"迟滞"卡片），免得用户以为是卡顿。

### 2.6 蜂鸣开关的作用域：只管"越限"，管不到安全功能

`buz_enable` 只作用于**数值越限**类报警（气体 / 温度 / 湿度 / 心率 / 血氧 / 光照）。

**刻意不作用于**摔倒报警、SOS 求助、网络失败提示 —— 那几项是安全功能和状态提示，
被静音会让设备"看起来正常"。这条在 `alarm_cfg.h` 与设置页界面上都写明了。

### 2.7 只有推送成功，才把门限落到本机 ★

本机保存的那份门限，语义是**"希望设备生效的那份"**。

**否掉的做法**：不管推送成不成功都先存本机。

**为什么否掉**：若推送失败也存，本机判读与设备判读就**永久性地不一致**了 ——
首页会说"温度超了 25℃"，而设备按 40℃ 在跑，蜂鸣器不响。那正是这个功能最不该
有的状态。（"推送成功"指巴法云 API 返回 `code:0`；设备是否真收到，由 cv 核对回答，
这两个层次故意分开。）

### 2.8 湿度：补上一个此前完全不存在的判据 ★

需求里只点名了温湿度和心率、气体，而湿度**此前根本没有任何门限** ——
读数有、判据没有，界面上湿度永远显示"相对湿度"。

本轮补上：`HUMI_HIGH_X10 900`（90%RH）/ `HUMI_LOW_X10 200`（20%RH），
固件、小程序、阈值设置页、趋势图阈值线四处一起加。

### 2.9 处理完配置就清空整个接收缓冲

**不这么做的后果**：一条已经处理过的配置报文会常驻环形缓冲。下一轮
`RxFind` 又找到它（它是缓冲里第一条），于是**新配置永远排在它后面**，
用户看到的现象是"改了不生效，要等 70 秒"。

代价是一个已知限制：**同一轮缓冲里如果有两条配置报文，只会应用先到的那条**
（见第七节）。

## 三、顺带修掉的三处错误（其中一处是白屏级）

写这一轮的交叉验证测试时，第 1、2 节（拿固件头文件逐项核对小程序里的镜像常量）
立刻就抓到两个**真实存在、且没人会发现**的错：

### 3.1 `THRESH.luxLow`：100 → 400

固件判暗用的是：

```c
uint16_t dark_th = raw.light_lux_valid ? LIGHT_DARK_LUX : LIGHT_DARK_RAW;
```

而 `LIGHT_CAL_ENABLED = 0`（没有标定）→ `lux_valid` 恒为 0 → **实际门槛是
`LIGHT_DARK_RAW = 400`**，且上报的 `"lux"` 字段就是 ADC 原始值
（`light_val = light_lux_valid ? light_lux : light_raw`）。

小程序里写的是 `100`（= `LIGHT_DARK_LUX`，**标定后**才成立的 lux 门槛）。
后果：**400 报"光照不足"的时候，小程序还在说"正常"**。

测试里同时加了一条**绊线**：断言 `LIGHT_CAL_ENABLED` 仍为 0。哪天有人把标定打开，
这条会失败并提示"THRESH.luxLow 必须改成 LIGHT_DARK_LUX"。

### 3.2 `THRESH.accelHigh`：2.5 → 1.8

固件已经是 `FALL_ACCEL_HIGH_G = 1.8f`（受 MPU6050 ±2g 物理量程限制，见 `docs/25`），
小程序里还停在早期的 `2.5`。后果：**1.8~2.5g 之间的撞击在设备上已经触发判决，
小程序却一个字都不提** —— 正是"设备在响、界面安静"这类最该避免的偏差。

### 3.3 `API_SENDMSG` 引用了尚未初始化的 `API_HOST` —— 会让小程序一打开就白屏 ★

`utils/bemfa.js` 里曾经把下发接口地址写在 `API_HOST` 之前：

```js
const API_SENDMSG = API_HOST + '/va/sendMessage'   // 上面还没定义 API_HOST
...
const API_HOST = 'https://apis.bemfa.com'
```

`const` 有暂时性死区，于是模块一被 `require` 就抛
`ReferenceError: Cannot access 'API_HOST' before initialization`。

**为什么编译期和语法检查都发现不了**：微信的编译只解析、不执行；
`wxmp_precheck.js` 用的是 `new vm.Script()`，同样只解析。
这类"跨语句的初始化顺序"错误**只有真正执行一次才会炸**。

这正是本轮新测试脚本的第一个动作就是 `require` 这个模块的原因 ——
它抓到了这个错。修法是把 `API_SENDMSG` 挪到 `API_HOST` 定义之后，与 `API_GETMSG` 并列。

## 四、界面

新增第三个 tab「阈值设置」（`pages/settings/`，四件套），实时页上也放了一个入口按钮。

| 区块 | 内容 |
|---|---|
| 当前读数 | 定时（30 秒）取一次最新报文，把实时的温度/湿度/心率/血氧/气体摆在对应滑块的**上方**，可以看着实时值定门限 |
| 指纹核对 | 本机 cv vs 设备 cv，三态：已生效 / 未同步 / 设备不支持回读（老固件） |
| 门限分组 | 温度（高/低）、湿度（高/低）、心率（上/下限）、血氧（下限）、气体 —— 每组一个滑块 + 加减按钮 + "按当前读数填" |
| 蜂鸣器 | 开关，并写明它管不到摔倒/SOS/网络失败 |
| 迟滞 | 把五个迟滞量列出来 |
| 下发 | 主题（可复制）、报文预览（可复制、显示字节数）、量程速查表、校验问题列表、「保存并下发设备」「恢复默认值」、下发结果 |

两个交互细节：

- **滑块用 `bindchange` 而不是 `bindchanging`**：拖拽过程中不 `setData`，
  避免几十次重渲染把界面拖卡；拖动时的数字由 slider 自带的 `show-value` 显示。
- **加减按钮按该组的步进走**（温度 0.5、其余 1），且在量程内夹紧 ——
  一路点下去不会造出一个必然被固件整条拒的值。

实时页与趋势页也跟着改了：

- `pages/index` 的判色（`buildView`）从读编译期常量改成读**本机保存的门限**，
  这样"界面说的"和"蜂鸣器做的"不会再各说各话；光照与撞击两项仍读常量（它们不在下发范围内）；
- 实时页新增**阈值预警横幅**，与原有的设备状态横幅是两件事：
  前者是固件自己的判定（蜂鸣器也由它驱动），后者是小程序侧的二次判读；

## 六、怎么演示（最实用的一条）

现场环境 26℃ 时，40℃ 的高温门限永远触发不了。所以：

1. 小程序 →「阈值设置」，看"温度"那一行右边的 `当前 26.4 ℃`；

   再减一格；

   设备信息里的「门限配置」显示 cv 与本机一致；

## 八、已知限制与后续

### 8.1 门限不持久（设计取舍，不是缺陷）

设备重启回出厂默认，小程序会显示"未同步"。这是 2.1 节那个取舍的直接后果，
补偿手段（cv 核对 + 重新下发按钮）已经就位。

### 8.2 同一轮缓冲里两条配置，只应用先到的那条

场景：用户在 10 秒内连改两次并各下发一次。两条例报文会落进同一个接收缓冲，
`net_poll_config()` 用 `ESP01S_RxFind` 找的是**缓冲里第一条** `"cfg":1`，
处理完**清空整个缓冲** → 后一条被吞掉。

现象与恢复：小程序显示 cv 未同步 → 点「重新下发」即可。**失败是可见且可恢复的**，
所以这一版先如实记下来，不改。

### 8.3 一个需要说清前提的理论风险：半条报文可能拼出"混血配置"

**前提条件较苛刻**，列在这里是因为后果（**静默应用一套错误门限**）比 8.2 严重，
而修法需要动固件的一个底层接口：

1. 缓冲里存在一个 `"cfg":1`，但从它往前 191 字节内**找不到 `'}'`**
   （报文被截断，例如 UART 丢字节），此时 `net_poll_config()` **不清缓冲**、直接返回；
2. 之后又来了**一条完整的**新配置；
3. 于是 `js[]` 从**旧的** `"cfg":1` 开始、到**新**报文的 `}` 结束 ——
   拼出一条前后不搭的报文。`find_first` 会取到旧报文里先出现的那些键，
   其余键取新报文的 → 一条"混血配置"，且**能通过校验**。

**为什么风险有界**：环形缓冲 1024 字节，设备每 10 秒产生的 AT 流量（遥测回环 +
AT 应答）约 150~250 字节，所以那段被截断的残留**约 50~70 秒后就会被覆盖**，
`RxFind` 也就不再找得到它。也就是说这个窗口只在截断发生后的一分钟内有意义，
而且一旦发生，cv 核对几乎必然报"未同步"（混血配置的指纹与用户发出的那套不同），
用户重新下发就会看到不一致。

**推荐的修法**（需要先给 `esp01s` 加一个"从指定位置起查"或"查最后一次出现"的能力，
`ESP01S_RxFind` 目前只返回首个匹配）：改成取缓冲里**最后一条** `"cfg":1` 起解析。
那样既消除混血，又顺带解掉 8.2。**在真机上验证过 AT 缓冲的边界行为之后再动。**

### 8.4 `/set` 推送能否真的到达设备：只能在设备上验

官方文档与本项目 `docs/09` 的 MQTT 实测都支持这个用法，但"设备在线时确实收到并生效"
只能在真机上看 cv 是否变成本机的那一个数。本轮的 144 项断言覆盖到"发出去的报文
与固件期望的一模一样"为止，**再往后的那一跳属于硬件验证范围**。
