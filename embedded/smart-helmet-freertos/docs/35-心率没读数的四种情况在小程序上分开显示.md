# 35 · "心率怎么没读数了"：四种"没读数"在小程序上分开显示

> 触发问题（用户原话）：
> **"我的心率怎么没读数了"**
>
> 实测日期：2026-09-21
> 涉及位置：小程序 `C:\Users\27362\Desktop\WeChat smart helmet`（**本轮没有改固件**）
>
> 结论一句话：**设备没坏，它测了 —— 只是没测出。** 实抓报文是
> `{"ps":3,"hr":null,"spo2":null}`：`ps=3` 表示"10 秒采集窗口已经跑完"，
> 而心率仍然是 null，只有一种解释 —— 窗口内合格搏动不足，判定"没测到"。
>
> 但**小程序把这个信息整个丢掉了**：固件每帧都在上报 `ps`（0 没手指 /
> 1 稳定中 / 2 采集中 / 3 测量完成），`parseTelemetry` 却没解析它，
> 于是界面对一切 `hr=null` 一律显示「未检测到（未佩戴 / 信号不足）」——
> "测完了没测出"被说成"没戴"，**方向直接指错**。
> 这一篇把 `ps` 接通，让四种情况在小程序上各说各的话。

---

## 一、先取证：设备到底在不在干活

不看日志、不猜，直接问云端。用只读的 HTTP 接口取最新一条
（**不建 MQTT 连接，不会顶掉板子**）：

```
GET https://apis.bemfa.com/va/getmsg?uid=<私钥>&topic=temp001&type=1&num=1
```

2026-09-21 16:39:17 取到的原文：

```json
{"ts":"10:01:49","seq":11,"hr":null,"spo2":null,"sc":0,"ps":0,"cv":38972,
 "t":28.6,"h":64.0,"gas":14,"lux":233,"ax":0.9,"ay":0.0,"az":0.0,
 "st":"normal","up":109123,"tsv":0}
```

两个独立的交叉验证，证明这条数据可信、设备正常：

| 证据 | 算法 | 结果 |
|---|---|---|
| `up` 与设备时间自洽 | 设备时间基准 10:00:00 + `up`(109.123s) = **10:01:49** | 与报文里的 `ts` **完全一致** |
| 云端时间与上报周期自洽 | 云端 `unix` 折算 16:39:12，本地取数 16:39:17 | 延迟 **6 秒**，上报周期 10 秒 |
| 运行时长 | `up`=109123ms | 设备 **109 秒前刚启动**（≈16:37:23） |

> `cv=38972` 正好是出厂默认指纹，`up` 只有 109 秒 —— 说明这是**刚烧录/复位后
> 的新一轮运行**，门限回到了出厂默认（RAM-only 的既定取舍，见 docs/34 第五节）。

## 二、关键一步：连续采样，抓住状态机的动作

单帧只能说明"取数那一刻的状态"。连续采 45 秒，把 `ps` 的走向摊开：

| # | 本机时刻 | seq | **ps** | 含义 | hr | spo2 |
|---|---|---|---|---|---|---|
| 1 | 16:40:05 | 15 | **2** | **采集中（MEASURING）** | null | null |
| 2 | 16:40:10 | 16 | **3** | **测量完成（DONE）** | null | null |
| 3 | 16:40:16 | 17 | 3 | 测量完成 | null | null |
| … | … | … | 3 | （保持冻结） | null | null |
| 10 | 16:40:51 | 20 | 3 | 测量完成 | null | null |

这一张表排除掉了三种猜测：

1. **不是"没接线/器件坏"** —— 器件不在总线上的话走不到 `ps=2`、更到不了 `ps=3`。
2. **不是"没放手"** —— `ps` 从 2 推进到 3，说明接触判定过了、13 秒流程跑完了。
3. **不是"设备停机"** —— `seq` 从 15 涨到 20，`up` 从 154458 涨到 202580
   （+48122ms，与真实过去的 41 秒同量级），运行连续、没有重启。

剩下的只有一种：**`HR_GetResult()` 给了 0**。

## 三、根因：`ps=3` + `hr=null` = "测完了但没测出"

固件的发布门控在 `heart_rate.c:827`：

```c
uint8_t pub = (s_state == HR_ST_DONE) ? 1 : 0;
if (bpm) *bpm = (pub && s_fin_bpm_valid) ? s_fin_bpm : 0;
return (uint8_t)(pub && s_fin_bpm_valid);
```

状态是 `DONE`（`ps=3`）却拿到 0，只能是 **`s_fin_bpm_valid == 0`** ——
即 10 秒窗口里合格的 IBI 少于门槛 `PPG_WIN_IBI_MIN = 3`。

**这个行为是设计，不是 bug。** 它是 docs/31 刻意做的取舍：

> 弱信号下要么给出偏差 ≤5 bpm 的结果，要么**明确不给结果**（不给随机数）。

`tools/ppg_measure_sim.py` 的实测量化了这一点：同一段弱信号跑 6 个噪声
realization，新版 **3 次给结果、3 次不给**；而旧版会给出 115/130 bpm
（真值 72）这种错值。屏上那句 `no pulse, retry` 是**诚实的**。

顺带排除"算法回归"：本轮重跑了两个仿真，**全部通过** ——

| 仿真 | 关键断言 | 结果 |
|---|---|---|
| `ppg_measure_sim.py` | 干净信号（幅度 600）在 40~150bpm **全部**通过门槛 | 全过 |
| `ppg_nopulse_sim.py` | 修复后 25 组里**一组错值都没有** | 全过 |
| `ppg_nopulse_sim.py` | 400ms 不应期 + 切迹抑制都在（`PPG_HR_MIN_IBI_MS=400`、`PPG_NOTCH_MIN_RATIO=0.60`） | 在 |

所以**算法主干没坏**，是这一段的实际信号落在了"宁可不说，也不给错数"的区间里。

## 四、真正的观测缺口：固件报了 `ps`，小程序把它丢了

固件是**一次测量**：贴手 → 稳定 3 秒 → 采集 10 秒 → 出结果并冻结。
`app_events.h:103` 把这个动机写得很清楚：

> 一次测量有 13 秒（3 秒稳定 + 10 秒采集）里 hr 是 null。
> 不带这个字段的话，收数据的人无法区分"没放手"、"正在测"、"测了但没测到" ——
> 这三种情况的 hr 都是 null，而它们对应完全不同的处置。

**问题是：小程序没接。** 改动前的三处：

| 位置 | 改动前 | 后果 |
|---|---|---|
| `utils/bemfa.js` `parseTelemetry` | 返回对象里**没有 `ps`** | 字段被整个丢弃 |
| `pages/index/index.js:616` | `hrNote = '未检测到（未佩戴 / 信号不足）'` | 四种情况一句话糊过去 |
| `pages/index/index.wxml` | 无 PPG 状态行 | 用户看不到设备在忙什么 |

实测抓到的正是最坏的那一格：**`{"ps":3,"hr":null}` 被显示成"未佩戴"** ——
用户于是去查佩戴（而佩戴没问题），真正该做的是**重测**。

## 五、修法：把 `ps` 翻成人话（只改小程序，不用重烧）

### 5.1 `utils/bemfa.js`

- `parseTelemetry` 增加 `ps: num(d.ps)`；老固件不带该字段时为 `null`
  （**刻意不默认成 0** —— 那会无中生有地说"没检测到手指"）。
- 新增 `ppgNote(d)`：`ps` → 一句可执行的话。
- 新增 `ppgStateText(ps)`：给设备信息区用的一行短标签。

| ps | 含义 | 小程序文案 |
|---|---|---|
| 0 | 没接触到皮肤 | 把指腹贴住光学窗口（两个小圆点那一面），不要隔外壳或保护膜 |
| 1 | 稳定中（3 秒） | 已检测到接触，正在稳定，之后才开始采集 |
| 2 | 采集中（10 秒） | 正在采集 10 秒窗口，保持不动；窗口跑完才发布结果 |
| 3 | **测量完成但没测出** | 本次测量已跑完，但没采到有效脉搏 —— **拿开手、重新贴一次再测** |
| null | 老固件 | 未检测到（未佩戴 / 信号不足） |

### 5.2 `pages/index/index.js`

- 心率、血氧的"没读数"文案改用 `bemfa.ppgNote(d)`。
- **`ps=3` 时卡片标 `v-warn` 而不是 `v-mute`** —— "测了没测出"是需要处理的
  状态，静默成灰色会让人以为"没戴、正常"。
- 血氧单列一句：`hr` 有值而 `spo2` 没有时，说明窗口本身是成功的，只是血氧那
  一路没成，不能复用"没采到脉搏"这句话。
- 设备信息区新增 `ppgText`。

### 5.3 `pages/index/index.wxml`

在"报文序号 seq"下方加一行「PPG 状态」。它描述的是**设备正在干什么**，
而不是某个读数的好坏，所以放在设备信息区而不是生命体征区。

## 七、诚实边界：这件事还没查到底

修好的是"**让小程序把话说对**"，不是"让心率一定测出来"。
**为什么这一段信号测不出，本轮没有定论**，因为决定性判据不在云端：

| 判据 | 在哪 | 云端有吗 |
|---|---|---|
| `d` = 红外直流分量（手指挡住多少光） | OLED 行 5 `PPG d:...` | **没有** |
| `a` = 交流峰值幅度（搏动有多强） | OLED 行 5 `PPG a:...` | **没有** |
| `SPO2:MAX30102 NG`（器件不在总线上） | OLED 行 1 | **没有**（`app_tasks.c:1160` 只写屏，不上报） |

所以设备端的三种"没数"在云端报文里长得**一模一样**。定论只能靠屏幕：

| OLED 行 1（心率行） | 行 5（PPG 调试行） | 结论 | 处置 |
|---|---|---|---|
| `PPG: put finger on` | — | 没判定到接触 | 指腹压住光学窗口，别隔着外壳 |
| `PPG: no pulse, retry` | `d` 大（几万）、`a` ≈ 0 | 有光、没搏动分量 | 压力过大/没对准/手在抖（docs/15 §4） |
| `PPG: no pulse, retry` | `d` ≈ 0 | 压根没采到光 | LED 电流 / 光学窗口被挡（docs/15 §3） |
| `SPO2:MAX30102 NG` | — | 器件不在 I2C 总线上 | 接线/供电/地址（docs/14） |

**关于幅度：这一段上一轮写错过一次，留个记录（2026-09-21 更正）。**

`user_config.h` 里 `PPG_LED_PA_RED/IR = 0x24`（≈7.2mA）确实是偏保守的一档，
docs/15 §3 给的调高路径是 `0x4F`（≈16mA）。但**不能据此断言实测幅度不足**：

- ❌ 上一轮写的"实测脉搏波幅度**只有 150 LSB**，漂移却到 400"是**错的**。
  150 和 400 是 `tools/ppg_measure_sim.py` 里弱信号场景的**仿真参数**
  （`WEAK = 150.0`、`DRIFT = 400.0`），不是任何一次实测。
- ✅ 工程里真正的实测样例是 `PPG d:58234 a:312`（docs/15 §二、docs/16 §四
  都引用了它），而 docs/16 对它的判定是**「光路完全打通了」** ——
  `a = 312` 落在 docs/15 判读表的「几百~几千」正常档，
  是 `PPG_PEAK_MIN_AMP = 30` 的十倍。

把仿真参数当实测值，会直接把「提高 LED 电流」误判成头号杠杆 —— 而 `a = 312`
这条数据恰恰说明**幅度可能不是主要嫌疑**。所以本轮改用仿真扫描来定量回答
（见 `tools/ppg_yield_sweep.py` 与 docs/36），而不是靠这个错误前提推理。

**但 `a = 312` 究竟是一次具体读数还是文档里的示例值，仍要实测确认**：
没有 `d`/`a` 的上行读数，就无法判断当前这次失败属于「幅度不够」还是
「波形形态不对」—— 这两种的处置方向完全相反。

## 八、下一次遇到"心率没读数"，按这个顺序看

1. 小程序「PPG 状态」那一行说的是什么？
   - `未检测到手指` → 去戴好；`稳定中`/`采集中` → **等着**，13 秒内 `--` 是正常的；
   - `测量已完成` + 心率 `--` → **拿开手重贴再测一次**（本次没采到有效脉搏）。
2. 重贴三次都不出 → 看 OLED 行 1 与行 5，按第七节的表对号入座。
3. 只在某一次不出、其余正常 → 属设计内的"宁可不说也不给错数"，
   与 docs/31 的取舍一致，不是故障。
