# 01 系统架构与任务设计

## 1. 交付物第 1 项：FreeRTOS 任务结构图（文字描述）

```
                        ┌──────────────────────────────────────────┐
                        │           中断层 (ISR)                    │
                        │  PA4 SOS 按键 EXTI4    USART1 RX 字节中断  │
                        └───────┬───────────────────────┬──────────┘
                                │ xQueueSendFromISR     │ 环形缓冲写入
                                │ (AlarmEvent_t)        │
                                ↓                       ↓
   ┌────────────────────────────────────┐   ┌───────────────────────────┐
   │ Alarm_Task              Priority 3 │   │  ESP01S 接收缓冲 (512B)    │
   │ 阻塞等 xQueueAlarmEvent            │   └────────────┬──────────────┘
   │  收到事件 → 抢占 → 蜂鸣器断续鸣响   │                │ 模式匹配
   │  → 写快照报警状态 → 到期恢复        │                │
   └───────┬────────────────────────────┘                │
           │ 写 s_snapshot (互斥)                        │
           ↓                                             │
   ┌──────────────────────────────────────────────────┐  │
   │             SystemData_t 全局快照                 │  │
   │        (xMutexSnapshot 保护, 无拷贝队列)          │  │
   └───────┬──────────────────────────┬───────────────┘  │
           │ 读(拷贝)                  │ 读(拷贝)          │
           ↓                          ↓                 │
 ┌────────────────────┐    ┌───────────────────────────┐│
 │ Display_Task  P=0  │    │ WiFi_Task          P=1    ││
 │ 500ms 周期刷 OLED   │    │ 等 10s 或 SOS 信号量        ││
 │ 持 xMutexI2C        │    │ → 组 JSON → MQTT PUBLISH  ││
 └────────────────────┘    └───────────┬───────────────┘│
                                       │ AT+CIPSEND      │
                                       └─────────────────┘
   
   ┌────────────────────┐  xQueueSensorRaw  ┌──────────────────────────┐
   │ Sensor_Task   P=1  │ ────────────────→ │ Data_Processing_Task P=2 │
   │ 100ms 周期          │  (SensorRaw_t,    │ 摔倒状态机 / PPG 心率      │
   │ 读 MPU/MAX30102/    │   长度 4)         │ 阈值判断 / 温度容错降级     │
   │ DHT11/DS18B20/MQ2, │                   │ → xQueueAlarmEvent        │
   │ 持 xMutexI2C        │                   │ → 写 s_snapshot           │
   └────────────────────┘                   └──────────────────────────┘
```

### 数据流一句话总结

**Sensor_Task（100ms 采样）→ 队列 → Data_Processing_Task（判定+组快照）→
{ Alarms→Alarm_Task 队列 | 快照→Display/WiFi 读取 }**；
SOS 按键走 **ISR → 队列直投 Alarm_Task + 信号量唤醒 WiFi_Task** 的旁路，不经过采样链路。

## 2. 任务参数表（交付物第 8 项）

| 任务 | 优先级 | 栈(字/字节) | 触发/周期 | 阻塞方式 | 占用 CPU 估计 |
|------|--------|-------------|-----------|----------|----------------|
| Alarm_Task | **3** 最高 | 128 / 512B | 阻塞等队列；报警时 50ms 切片 | `xQueueReceive(portMAX_DELAY)` | 仅报警期间 |
| Data_Processing_Task | 2 | 256 / 1KB | 阻塞等队列（实际约 100ms 一次） | `xQueueReceive(portMAX_DELAY)` | 每 100ms 约 0.3ms |
| Sensor_Task | 1 | 256 / 1KB | **100ms**（`vTaskDelayUntil`） | `vTaskDelayUntil` | 每 100ms 约 2~8ms |
| WiFi_Task | 1 | 384 / 1.5KB | **10s** 或 SOS 信号量 | `xSemaphoreTake(超时=10s)` | 每 10s 峰值约 50ms |
| Display_Task | **0** 最低 | 256 / 1KB | **500ms** | `vTaskDelay(500)` | 每 500ms 约 30ms（I2C 传输为主） |

> **优先级 0 的说明**：FreeRTOS 空闲任务优先级也是 0。Display_Task 与其同级，
> 在 `configUSE_TIME_SLICING = 1` 下时间片轮转；因为 Display_Task 每轮都会调用
> `vTaskDelay()`，不会饿死空闲任务。若要求业务任务严格高于空闲任务，可整体上移
> 一级（Display=1、Sensor=2、DataProc=3、Alarm=4），相对顺序不变。
>
> **WiFi_Task 优先级**：需求未指定，本设计取 1。理由是 AT 交互存在数十毫秒级
> 阻塞（`AT+CWJAP` 最长等 20s），让它低于 DataProc/Alarm 才能保住报警实时性。

### 各任务延时参数与依据

| 参数 | 值 | 依据 |
|------|-----|------|
| `SAMPLE_PERIOD_MS` | 100 | 需求指定 |
| `DISPLAY_PERIOD_MS` | 500 | 需求指定 2000，现场演示要求更快刷新，**调快至 500（4x）**；见 `user_config.h` 第四节说明 |
| `UPLOAD_PERIOD_MS` | 10000 | 需求指定 30000，现场演示要求云端数据更新更密，**调快至 10000（3x）**；一轮上报约 1~2s，余量充足 |
| `DHT11_PERIOD_MS` | 2000 | DHT11 要求两次读取间隔 ≥1s（数据手册），取 2s 留余量 |
| `DS18B20_PERIOD_MS` | 1000 | 12 位分辨率转换时间较长，采用"发命令 → 1s 后取结果"的两阶段读取，避免阻塞 |
| `MQTT_KEEPALIVE_S` | 30 | 10s 上报本身就是流量；另在 15s 处补一次 `PINGREQ` |

## 3. 任务间通信对象清单

| 对象 | 类型 | 长度/容量 | 生产者 | 消费者 | 说明 |
|------|------|-----------|--------|--------|------|
| `xQueueSensorRaw` | Queue | 4 × `SensorRaw_t`(约 76B) | Sensor_Task | Data_Processing_Task | 队列满则丢弃新帧并计数，不阻塞采样节奏 |
| `xQueueAlarmEvent` | Queue | 8 × `AlarmEvent_t`(约 32B) | DataProc / WiFi / **EXTI ISR** | Alarm_Task | ISR 用 `xQueueSendFromISR` |
| `xSemSosUpload` | Binary Semaphore | — | EXTI ISR | WiFi_Task | 让 SOS 绕过 10s 周期立即上报 |
| `xMutexI2C` | Mutex | — | — | Sensor_Task / Display_Task | I2C1 上挂 3 个器件，HAL 阻塞式传输不可并发 |
| `xMutexSnapshot` | Mutex | — | Alarm_Task(写状态)、DataProc(写数据) | Display/WiFi(读) | 无拷贝队列：始终只有一份最新快照 |

### 为什么快照用"互斥锁 + 全局结构体"而不是队列

如果 Display 和 WiFi 各用一条队列取快照，两者消费速度不同（500ms vs 10s），
旧数据会在慢队列里堆积，内存与时效都吃亏。改成"最新一帧 + 互斥保护"后，
任何消费者拿到的都是当前最新状态，且不占额外队列内存。

## 5. 资源预算（F103C8T6：64KB Flash / 20KB RAM）

RAM 实际占用（**以下为 Keil 链接后的实测结果**，可直接用
`MDK-ARM/smart-helmet-freertos/smart-helmet-freertos.map` 复核）：

| 项目 | 占用 |
|------|------|
| FreeRTOS 堆（`configTOTAL_HEAP_SIZE = 10240`） | 10240 B |
| ├ 任务栈（Alarm 192 + DataProc 256 + Sensor 256 + WiFi 384 + Display 256 字） | 5376 B |
| ├ 空闲任务栈（128 字） | 512 B |
| ├ 队列（SensorRaw 4×N + Alarm 8×32）与信号量/互斥量 | ≈ 1450 B |
| └ heap_4 块头开销 | ≈ 150 B |
| OLED 显存 `s_buf[8][128]` | 1024 B |
| 心率环缓（IR + RED 各 200 × uint16） | 800 B |
| JSON / MQTT 报文缓冲 | 448 + 640 = 1088 B |
| ESP01S 接收环形缓冲 | 512 B |
| 快照 + 各驱动/任务静态变量 | ≈ 700 B |
| Keil 启动文件的 main 栈（0x400）与 Heap（0x200） | 1536 B |
| **合计（链接器实测 ZI 16160 B + RW 304 B）** | **16464 B / 20480 B（80.4%）** |

> 余量约 **4.0 KB**。任务栈是从 FreeRTOS 堆里切出来的，所以调整栈深不会改变
> ZI 大小，但会改变堆内余量 —— 堆余量不足会让 `xTaskCreate` 失败，
> 而 `APP_TasksCreate()` 已经对该返回值做了检查（失败即停机蜂鸣），
> 不会出现"静默少一个任务"的情况。
>
> 另外 `APP_ReportStackUsage()` 会在运行期每 10 秒从 USART2 打印各任务
> 剩余的栈（`uxTaskGetStackHighWaterMark`），**栈该给多大以这个实测值为准**。

Flash 实测（**以链接结果为准**）：

| 项目 | 占用 |
|------|------|
| Code | 31734 B |
| RO-data | 1394 B |
| RW-data（需复制到 RAM 的初值） | 304 B |
| **合计** | **33432 B / 65536 B（51.0%）** |

> 说明：本工程用的是**标准 C 库（未勾选 MicroLIB）**，且只使用 `snprintf`
> 做格式化、刻意不用 `%f`（小数一律按"整数×10"手工拼字符串）。
> 若改用 `%f`，Flash 会明显增大。当前 51% 的占用留有充足空间。

## 6. 实时性与抖动分析（诚实标注）

| 场景 | 最坏延迟 | 原因 |
|------|----------|------|
| SOS 按键 → 蜂鸣器响 | < 1ms + 临界区 | ISR 直投最高优先级任务，`portYIELD_FROM_ISR` 立即切换 |
| 摔倒判定 → 蜂鸣器响 | 约 0.1~1ms（含队列） | 判定发生在 DataProc（P=2），Alarm(P=3) 立刻抢占 |
| 上述两类的最坏干扰 | 最长约 6ms | DHT11（约 3~4ms）、DS18B20（约 5~6ms）位翻转期间关中断 |
| OLED 刷新占用总线 | 约 25~30ms（400kHz） | 整屏 1024 字节阻塞式 I2C 传输；期间传感器读取等互斥锁 |

结论：报警链路的最坏延迟在**毫秒级**，满足安全帽场景；但必须如实承认
"单总线传感器关中断 4~6ms" 是这套方案的主要抖动来源。若需要更严格的抖动
指标，应改用带硬件外设的方案（如 DS18B20 用 UART 单线模式、DHT 类传感器
交给协处理器），本设计不假设这些硬件存在。
