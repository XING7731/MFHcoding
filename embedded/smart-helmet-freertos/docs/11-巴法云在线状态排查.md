# 11 · 巴法云显示"离线"的排查（数据其实已经上云）

> 适用现象：**联网稳定了、日志里也在正常上报，但巴法云控制台的设备图标一直是灰的（离线）。**
> 本文记录根因、实测证据、修复方式与验证方法。

---

## 一、结论先行

**巴法云控制台的"在线/离线"判据是：这个主题上有没有订阅者。**
它既不是"TCP 有没有连着"，也不是"有没有在发数据"。

设备只发 `PUBLISH`、从不 `SUBSCRIBE` 时：

- 数据**能**成功上云，云端也**能**看到最新消息；
- 但控制台图标**永远是灰的**。

修复方式：`MQTT CONNECT` 成功之后补发一条 `SUBSCRIBE <同一个主题>`，并维持长连接。
本工程已在固件里实现（`mqtt_client.c` 的 `MQTT_Subscribe`），每次重连后会自动重新订阅。

---

## 二、实测证据（关键的一步）

巴法云提供设备接口，对每个主题返回**两个互相独立**的在线标志：

```
online     该主题「有没有订阅者在线」   ← 控制台图标显示的就是这个
pubOnline  该主题「发布者是否在线」
```

接口：`https://cloud.bemfa.com/docs/src/api_device.html`

```
http://apis.bemfa.com/vb/api/v2/allTopic?openID=<私钥>&type=1     # type=1 是 MQTT
```

用本项目私钥实测（脚本：`tools/bemfa_online_probe.py`）：

| 时机 | online | pubOnline |
|---|---|---|
| 基线（本机未连接、未订阅） | **false** | true |
| 连上去 `SUBSCRIBE temp001` 并保持连接 | **true** | true |
| 断开连接后再查 | **false** | true |

一次订阅让 `online` 由 `false` 翻成 `true`，断开又翻回去 —— **判据确认无疑**。

同时 `pubOnline` 在整个过程中一直是 `true`：这说明**已经有一路连接在往这个主题发布数据**（也就是开发板），
换言之 **上报本来就是成功的**，问题从来不在数据通路上。

> 复现命令：
> ```bash
> python tools/bemfa_online_probe.py --uid <私钥> --topic temp001 --hold 36
> ```
> 脚本会自动做"基线 → 订阅保持 → 断开"三段对比并打印结论。

---

## 三、为什么以前不容易发现

原固件的 MQTT 客户端只实现 4 种报文：

```
CONNECT / PUBLISH / PINGREQ / DISCONNECT          ← 没有 SUBSCRIBE
```

MQTT 协议本身并不要求发布者订阅，所以代码逻辑上没有"错"；
但巴法云把"在线"绑定在**订阅**上，于是形成一个很隐蔽的落差：

```
链路完全正常 → 数据上云正常 → 控制台却显示离线
```

这一层落差无法从"连没连上""发没发成功"看出来，只能对照云端接口的 `online` 字段才暴露。

---

## 四、修复内容

### 1. `mqtt_client.c` / `mqtt_client.h`：新增 SUBSCRIBE

报文布局（MQTT 3.1.1）：

```
固定头   0x82 <剩余长度>
可变报头 报文标识符(2 字节) = 0x00 0x01
载荷     主题长度(2) + 主题 + 请求的 QoS(1) = 0x00
```

应答 SUBACK：

```
0x90 <剩余长度=3> <报文标识符 2 字节> <返回码 1 字节>
返回码 0x00/0x01/0x02 = 订阅成功(按该 QoS 生效)；0x80 = 失败(主题不存在/无权限)
```

接口：

```c
uint8_t MQTT_Subscribe(const char *topic_filter);   /* 0=成功 1=参数/TCP 2=被拒 3=超时 */
uint8_t MQTT_GetLastSubackRc(void);                 /* SUBACK 返回码; 0xFF = 没收到 */
```

### 2. `app_tasks.c`：建链流程从 5 步变 6 步

```
1/6  AT 握手
2/6  连热点
3/6  TCP 连 Broker
4/6  MQTT CONNECT
5/6  SUBSCRIBE 主题      ← 新增（决定控制台在线/离线）
6/6  就绪
```

**订阅失败不判为断线**：数据上报完全不受影响，只是控制台显示离线，
因此它被记成一条**独立诊断**（`NET_DIAG_SUB_FAIL`）而不是重连理由 ——
避免用户为了一个灰色图标去做无谓的断连重连。

同时 `WiFi_Task` 里每次上报成功**不会**再无条件把状态刷成 `ONLINE`：
如果本轮订阅失败，屏幕会一直保留 `NET: sub rc=XX`，否则用户看到 `NET: OK pub=N`
会以为一切正常，却在控制台里怎么也找不到设备。

### 3. `user_config.h`：开关

```c
#define MQTT_SUBSCRIBE_ENABLE 1     /* 1 = 连接后订阅主题(控制台显示在线) */
```

置 0 只在特殊场景需要（例如要让另一个客户端独占订阅）。

### 4. OLED 新增一条诊断

| 屏上显示 | 含义 | 处置 |
|---|---|---|
| `NET: OK pub=N` | 已连接 + 已订阅 + 已上报 N 次 | 控制台应显示**在线** |
| `NET: sub rc=80` | 订阅被拒（主题不存在/名字写错） | 去 MQTT 控制台核对主题名 |
| `NET: sub rc=FF` | 没收到 SUBACK（链路被掐断） | 数据仍能上云，查链路稳定性 |
| `NET: MQTT rc=05` | CONNECT 就被拒（私钥/授权） | 见 docs/08 |

## 五、烧录后如何确认

1. 看串口（USART2 / PA2-PA3，115200）：

   ```
   [NET] 1/6 AT check...
   [NET] 2/6 join AP...
   [NET] 3/6 tcp connect bemfa.com:9501...
   [NET] 4/6 mqtt connect...
   [NET] 5/6 subscribe temp001...
   [NET] 6/6 connected + subscribed: console shows ONLINE
   ```

   看到 `6/6` 即表示订阅成功。

2. **在电脑上用接口确认**（最直接，不依赖肉眼看控制台）：

   ```bash
   python tools/bemfa_online_probe.py --uid <你的私钥> --topic temp001 --hold 6
   ```

   只需看第一段输出：若 `online=True`，说明此刻**确实有订阅者在线**（那就是你的设备）。

   或用一条命令直接读：

   ```
   http://apis.bemfa.com/vb/api/v2/allTopic?openID=<私钥>&type=1
   ```

   关注返回里的 `"online":true`。

3. 注意：**同一私钥只允许一个 MQTT 连接。**
   如果你用 MQTTX / mqtt.fx 以同一私钥连上去调试，会把设备顶下线（反之亦然）——
   此时 `online` 可能显示为 true，但那"在线的订阅者"其实是你的调试客户端，不是设备。
   调试时建议临时改用另一个私钥，或先给设备断电。

---

## 六、附带发现：主题名会被控制台记录成中文"设备名"

上面接口返回里，`temp001` 的 `name` 是 **"插座"**、`deviceType` 是 `outlet` —— 这是
在 MQTT 控制台建主题时选的设备类型默认值，不影响功能，可以忽略；
若想让控制台显示得更清楚，可在控制台把该主题的**名称**改成"安全帽"之类，`deviceType` 保持默认即可。

---

## 七、一句话总结

> **"连不上云"和"控制台显示离线"是两件事。**
> 前者看 CONNACK（docs/08）；后者看订阅（本文）。
> 数据其实一直在上云 —— `pubOnline=true` 就是证据。
