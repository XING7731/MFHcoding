## 2. 接入前工程的状态（为什么要做这些改动）

原始工程是用 CubeMX 新建的、几乎为空的骨架：

| 现状 | 影响 |
|------|------|
| `.ioc` 只配了 NVIC / RCC / SYS | 没有 USART / I2C / ADC / RTC / TIM 任何一个外设 |
| `Core/Src` 只有 `main.c` `gpio.c` `stm32f1xx_hal_msp.c` `stm32f1xx_it.c` | 没有外设初始化代码 |
| `Drivers/CMSIS/RTOS` 下只有一个 `cmsis_os.h` 模板 | **完全没有 FreeRTOS 内核源码** |
| `stm32f1xx_hal_conf.h` 只开了 GPIO/CORTEX/DMA/FLASH/EXTI/PWR/RCC | `ADC_HandleTypeDef`、`I2C_HandleTypeDef`、`RTC_HandleTypeDef` 等**全部未定义** |
| `uvprojx` 里没有 FreeRTOS 分组、没有 FreeRTOS 头文件路径 | `FreeRTOS.h` 找不到 |
| `user/` 目录在工程文件夹**外面**（用 `..\..\user\` 引用） | 工程不自包含，一挪动就断 |
| 工程里同时存在 `Core/Src/main.c` 和 `user/Src/main.c` | `main()` 重复定义 |

首次编译（基线）结果为 **53 个错误 / 24 个警告**。

## 4. 过程中发现并修掉的真实缺陷

以下都是**代码本身的缺陷**，不是工程配置问题。它们原先只是"没能编译到"，
一旦接入工程就会暴露。

### 4.1 armcc (AC5) 按 GBK 解析源码 → 中文字符串吃掉结束引号

**症状**：

```
error:  #8: missing closing quote
   const char *f(void) { return "鎽斿€掓姤璀?"; }
```

报错信息里的 `鎽斿€掓姤璀?` 正是 `摔倒报警` 的 UTF-8 字节被当 GBK 解读的乱码
——**这是识别该问题的特征**。

**根因**：ARMCC AC5 按"系统 ANSI 代码页"（中文 Windows 上为 GBK）解析源文件。
UTF-8 中文在字符串字面量里被两两配对，错位时恰好把结尾的 `"` 当成某个双字节
字符的第二字节吃掉。注释里的中文不受影响（词法分析时会跳过注释，且实测其它
文件的注释均正常编译）。

实测：加 `--multibyte_chars` **无效**；换 AC6 (armclang) 可以，但本工程用 AC5。

**解决**：把字面量里的非 ASCII 字节写成 `\xNN`，源码层面变成纯 ASCII，
运行期字节流完全不变：

```c
return "摔倒报警";
    ↓
return "\xe6\x91\x94\xe5\x80\x92\xe6\x8a\xa5\xe8\xad\xa6";
```

工具：`tools/fix_cn_literals.py`（带状态机，只改代码中的字面量，不碰注释）。

> **以后自己加中文提示时**：要么先跑一次这个脚本，要么直接把中文写成 `\xNN`。
> 注意 `\xNN` 会贪婪吞掉后续十六进制字符，脚本已自动处理（必要时用 `""` 断开）。

### 4.2 用了 STM32F4 的 RTC API，而 F1 的 RTC 是老式版本

STM32F1 的 RTC 是 **RTC v1**，结构与 F4/F7/L4（RTC v2）不同：

| 成员 | F1 | F4 |
|------|----|----|
| `RTC_TimeTypeDef` | 只有 `Hours` / `Minutes` / `Seconds` | 另有 `TimeFormat` / `DayLightSaving` / `StoreOperation` |
| `RTC_InitTypeDef` | 只有 `AsynchPrediv` / `OutPut` | 另有 `SynchPrediv` / `OutPutPolarity` / `OutPutType` |

**症状**：

```
error:  #136: struct "<unnamed>" has no field "TimeFormat"
error:  #20:  identifier "RTC_HOURFORMAT12_AM" is undefined
error:  #136: struct "<unnamed>" has no field "SynchPrediv"
```

**解决**：
- `rtc_time.c`：去掉 F4 专有的三个字段；
- `main.c`：`AsynchPrediv` 改用 **`RTC_AUTO_1_SECOND`**，让 HAL 依据实际
  RTC 时钟频率自动算分频，LSE / LSI 两种情况下都能得到 1 秒时基。

### 4.3 板上没有 32.768kHz 晶振会导致上电"没反应"

原 `SystemClock_Config()` 无条件要求 `RCC_LSE_ON`。但常见的 Blue Pill /
最小系统板**只焊了 8MHz 晶振**，此时 `HAL_RCC_OscConfig()` 因等不到 LSE 就绪
返回 `HAL_ERROR` → `Error_Handler()` → 蜂鸣器长鸣、程序卡死。现场表现就是
"上电没反应"，且很难查。

**解决**：两级尝试 —— 先试 HSE + LSE；失败则关掉 LSE 只配 HSE+PLL，
RTC 改用 **LSI**（精度较差，故固件同时上报 `uptime_ms` 与
`timestamp_valid`，便于上位机判断时间是否可信）。

### 4.4 MQTT CONNECT 报文缓冲区溢出（写越界 2 字节）

```c
uint8_t vh[8];                       /* ← 太小 */
...
vh[vh_len++] = 0x00;                 /* 协议名长度 */
vh[vh_len++] = 0x04;
memcpy(&vh[vh_len], "MQTT", 4);
vh[vh_len++] = 0x04;                 /* 协议级别 */
vh[vh_len++] = flags;                /* 连接标志 → vh_len = 8 */
vh[vh_len++] = (uint8_t)(MQTT_KEEPALIVE_S >> 8);   /* ← 越界！ */
vh[vh_len++] = (uint8_t)(MQTT_KEEPALIVE_S & 0xFF); /* ← 越界！ */
```

MQTT 3.1.1 的 CONNECT 可变报头固定 **10 字节**，`vh[8]` 会写越界 2 字节。

**发现方式**：armcc 报 `C4488E: write to variable 'vh' with offset out of bounds`。
**解决**：改为 `uint8_t vh[10];`。

### 4.5 `DBG` 宏会越界读取栈数据并通过串口发出去

```c
#define DBG(...) do { char _b[112]; int _n = snprintf(_b, sizeof(_b), __VA_ARGS__); \
                      if (_n > 0) HAL_UART_Transmit(&huart2, (uint8_t *)_b,        \
                                                    (uint16_t)_n, 100); } while (0)
```

`snprintf` 返回的是**"假如缓冲区足够大、本应写入的长度"**，它可能大于缓冲区。
例如 `DBG("[NET] published: %s\r\n", s_json)` 中 `s_json` 最长 448 字节，
`_n` 会远大于 112，于是 `HAL_UART_Transmit` 从 112 字节的栈缓冲**越界往后读**，
把栈上的其它数据当调试信息发出去。

**解决**：发送前把 `_n` 截断到 `sizeof(_b) - 1`；并加了 `DBG_ENABLE` 开关。

### 4.6 其余编译期问题

| 问题 | 解决 |
|------|------|
| `FreeRTOS.h` 找不到 | `uvprojx` 加入 FreeRTOS 的两条包含路径 |
| `PPG_BATCH_MAX` 未定义（`heart_rate.c`） | 补 `#include "app_events.h"`（该宏其实定义在 `app_events.h`） |
| `MQTT_BUF_SIZE` 未定义（`mqtt_client.c`） | 同上 |
| `HAL_ADCEx_InjectedConvCpltCallback` 未定义（链接期） | `hal_adc.c` 会引用它，其弱定义在 `stm32f1xx_hal_adc_ex.c`，故补入该源文件 |
| `write_cmd()` 声明但未引用 | 删除 |
| `main()` 重复定义 | 从工程移除 `Core/Src/main.c` |

### 5.1 编译结果

```

Program Size: Code=31734  RO-data=1394  RW-data=304  ZI-data=16160
FromELF: creating hex file...
"smart-helmet-freertos.axf" - 0 Error(s), 0 Warning(s).
```

| 项 | 值 |
|----|-----|
| Flash | `31734 + 1394 + 304 = 33432` B / 65536 B = **51.0%** |
| RAM | `16160 + 304 = 16464` B / 20480 B = **80.4%** |
| FreeRTOS 堆 | `ucHeap` = 10240 B（map 中可查） |

### 5.2 关键符号的归属（来自 `.map`，用于确认接线正确）

| 符号 | 来自 | 说明 |
|------|------|------|
| `SVC_Handler` | `port.o` | FreeRTOS 移植层接管 |
| `PendSV_Handler` | `port.o` | 同上 |
| `SysTick_Handler` | `port.o` | SysTick 归 FreeRTOS |
| `TIM2_IRQHandler` | `stm32f1xx_hal_timebase_tim.o` | HAL 1ms 时基 |
| `HAL_InitTick` | `stm32f1xx_hal_timebase_tim.o` | 覆盖了 `hal.o` 中的弱定义 |
| `HAL_MspInit` | `stm32f1xx_hal_msp.o` | 全工程唯一一份定义 |
| `main` | `main_1.o`（即 `user/Src/main.c`） | 全工程唯一一个 main |
| `xTaskCreate` | `tasks.o` | FreeRTOS 内核已链入 |

### 5.3 中断优先级的一致性检查

- `configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY = 5`
  （`FreeRTOSConfig.h`）
- `USART1_IRQn` 与 `EXTI4_IRQn` 抢占优先级均设为 **5**（`main.c` 中）
- TIM2（HAL 时基）优先级为 `TICK_INT_PRIORITY = 15`，不调用 FreeRTOS API，合规

> 这两处是**强耦合**的：若改动任一处的优先级，必须同步核对另一处，
> 否则会出现断言失败或系统跑飞。

## 6. 烧录与验证步骤

1. **打开工程**：双击 `MDK-ARM/smart-helmet-freertos.uvprojx`。
2. **编译**：Project → Rebuild all（应得到 0 Error / 0 Warning）。
3. **确认下载器**：Options for Target → Debug，选择你的 ST-Link / J-Link
   （本工程未固定下载器，需按你的硬件选）。
4. **烧录**：也可直接用 `MDK-ARM/smart-helmet-freertos/smart-helmet-freertos.hex`。
5. **接串口看自检输出**：USART2 = **PA2/PA3，115200-8N1**。
   上电后应周期性看到：
   - `[STACK] Alarm=..w DataProc=..w Sensor=..w WiFi=..w Display=..w`
     → **每 10 秒一次的任务栈余量实测**。某一路接近 0 就把对应任务的栈调大
     （`user/Src/app_tasks.c` 的 `APP_TasksCreate()`），并确认堆还有余量。
   - `[NET] ...` 联网过程的阶段性输出（若已配置好 WiFi）
   - `[ALARM] ...` 报警事件
6. **OLED**：上电应先显示 `SMART HELMET` / `FreeRTOS booting`，
   随后进入 7 行数据刷新（时间 / HR·SpO2 / 温度·湿度 / 气体 /
   三轴加速度 / 状态 / 运行时长）。

> 若蜂鸣器**长鸣不停**，说明初始化失败或栈溢出，请按
> `docs/04-调试验收清单.md` 逐项排查；`vApplicationStackOverflowHook`
> 与 `Error_Handler()` 都会长鸣，可在调试器里打断点区分。
