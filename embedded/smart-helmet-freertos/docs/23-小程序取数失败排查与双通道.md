# 23 · 小程序取数失败排查 + 双通道取数

**背景**：微信小程序监控端上线后报「获取数据失败」，用户已在微信公众平台配置了合法域名。

**结论**：`apis.bemfa.com` 与 `api.bemfa.com` 是**两个不同域名**，巴法云官方小程序教程里
写的是后者（`api`，少一个 `s`），而代码请求的是前者。白名单不认子域，配错就整条失败；
更要紧的是 —— **`api.bemfa.com` 上根本没有可用的取数接口**。已改为双通道，并把诊断做成
一次点击即可定位。

---

## 1. 先排除"网络/证书"这类常见猜测

真机失败而电脑能通时，最先被怀疑的通常是 TLS。实测排除：

| 检查项 | 结果 |
|---|---|
| 域名解析 | `apis.bemfa.com` / `api.bemfa.com` → **43.139.93.44**（同一个 IP）；`bemfa.com` → 119.91.109.180 |
| 证书 | `CN=*.bemfa.com`，签发 `Asseco Data Systems S.A.`，有效期至 2026-11-10 |
| 证书链 | 完整（含中间证书，跨签至 Certum 根） |
| TLS 版本 | 1.2 / 1.3 均支持 |
| 小程序 UA 请求 | 正常 200 |

→ **TLS/DNS 不是原因**。这也顺手解释了一件事：既然两个主机解析到同一 IP，
那么"能不能访问"不是问题，问题只在**微信白名单认的是哪个字符串**。

---

## 2. 根因：官方教程给的域名取不到数据

巴法云官方小程序示例文档写的是：

> 在 **request 合法域名**处，和 **socket 合法域名**处，分别添加域名
> `https://api.bemfa.com` 和 `wss://bemfa.com`

而本工程代码请求的是 `https://apis.bemfa.com`。

穷举实测（`tools/wxmp_host_probe2.py`，2 主机 × 6 路径 × 7 组参数）：

| 主机 | 可用组合 |
|---|---|
| `apis.bemfa.com` | ★ `/va/getmsg?uid=&topic=&type=1`（HTTP 200, code=0, 有数据）<br>★ `/vb/api/v2/allTopic?openID=&type=1`（同上） |
| `api.bemfa.com` | **一组都没有**。`/va/getmsg` → **404**（nginx 默认页）<br>`/api/device/v1/data/1/get/` → HTTP 200 但 `code=40012`（topic error），换 7 组参数分别得 40012 / 41020 / 41021 |

**所以：只要按官方教程把 `api.bemfa.com` 配进白名单，就一定取不到数** ——
既是白名单不匹配，也是该主机本身没有这个接口。

> 两个域名的关系：解析到同一 IP，但路由不同。
> `apis.*` 走的是新版 `/va/*` 接口；`api.*` 上只剩旧版 `/api/device/v1/*`，
> 且旧接口对本项目主题返回 topic error。

---

## 3. 修复方案：双通道

小程序能用的两类域名（request / socket）在微信里是**两个独立配置项**，
只配一栏时另一条必然失败。因此两条都实现，任意一条通即可用。

| 通道 | 地址 | 白名单栏位 | 实测 |
|---|---|---|---|
| WSS 实时推送 | `wss://bemfa.com:9504/wss` | socket 合法域名 | ✅ 已收真实推送 |
| HTTP 轮询 | `https://apis.bemfa.com/va/getmsg` | request 合法域名 | ✅ 已取到真实数据 |

默认通道 `auto`：**先试 WSS（12 秒窗口），连不上自动退回 HTTP 轮询**，
并在界面上明确标出「HTTP 轮询（已降级）」+ 原因。也可手动锁定单条通道。

### 3.1 WSS 通道：为什么手写 MQTT 而不装 mqtt.js

小程序装 npm 包需要额外"构建 npm"，多一道容易出错的环节。MQTT 3.1.1 只需
**CONNECT / SUBSCRIBE / PINGREQ / DISCONNECT** 四种上行 + **CONNACK / SUBACK / PUBLISH / PINGRESP**
四种下行，报文格式很小，手写约 200 行且完全可控（出问题能直接读代码定位）。

`utils/mqttws.js` 的接口：

```js
mqttws.connect({
  url: 'wss://bemfa.com:9504/wss',
  clientId: uid,          // 巴法云要求 ClientID = 私钥
  topic: topic,
  keepAliveSec: 60,
  onStatus: (text, detail) => {},   // 连接过程上报，用于界面显示
  onMessage: (payload, topic) => {},// 收到设备报文
  onError: (e) => {},
  reconnect: false        // 重连由页面统一管，避免与降级逻辑打架
})
```

### 3.2 互踢探测（关键，因为它决定 WSS 能不能用）

巴法云同一私钥只允许一个 MQTT 客户端在线。板子已用该私钥连接，若小程序再用同一
ClientID 连接就会**把板子顶下线**，那是灾难性的。

`tools/wxmp_wss_test.js` 专门做了这个探测：连接 WSS 前后各用 HTTP 接口读一次板子的 `seq`，
并在接收期间观察 `up`（运行时长）是否连续。

实测结果（两次独立运行一致）：

```
连接前 HTTP 侧读到: seq=211
  [status] MQTT 已连接 (CONNACK)
  [status] 已订阅 temp001 (SUBACK)
  [push ] seq=212 up=2225077
  [push ] seq=213 up=2235449     ← 相邻差值 10272ms
  [push ] seq=214 up=2245817     ← 相邻差值 10268ms（周期稳定 10.3s，无重启痕迹）
接收期间 HTTP 侧读到: seq=214
```

`up` 平滑递增且步长一致 ⇒ 板子期间**没有掉线也没有重连**。**结论：WSS 与板子可共存，不会互踢。**

> 注意适用范围：这只说明"小程序 WSS 通道"不会顶掉板子。
> 用 MQTTX / 网页控制台以同一私钥登录仍可能顶掉，排查时避开。

## 4. 一并修掉的两个隐患

### 4.1 原始 errMsg 被"翻译"覆盖了

早期版本把 `wx.request` 给的原始 `errMsg` 用我推测的原因**覆盖**掉了。
一旦失败原因不在推测表里，唯一的一手线索就丢了，只能来回猜。
现在两者都留：`errMsg`（建议怎么办）与 `errRaw`（原文证据）分两行显示。

### 4.2 在线判据不能绑定"请求成功"

HTTP 请求成功 ≠ 设备在线。板子停机后平台接口照样返回那条老记录，请求一路 200 ——
只看请求成功，界面会**永远显示"在线"**。

改为**把在线判据绑在 `seq` 变化上**：只有收到新 `seq` 才推进"最近活动时刻"，
再把当前时间与该时刻的差拿去判在线/延迟/离线。另加 3 秒心跳定时器把状态刷到界面
（推送模式下设备停掉后不再有数据到达，没有它界面会停在最后一条的"在线"上）。

## 5. 验证

三套脚本，共 **148 项断言**，全部通过：

| 脚本 | 覆盖 | 断言 |
|---|---|---|
| `wxmp_bemfa_test.js` | 报文解析、13 种状态映射、去重、缓存、重启识别 | 58 |
| `wxmp_wss_test.js` | MQTT 报文编解码（含粘包/半包/变长编码边界）+ **真连巴法云收推送** + 互踢探测 | 39 |
| `wxmp_page_test.js` | 驱动真实页面代码：双通道渲染、重复轮询去重、停机判离线、降级、诊断 | 51 |

`wxmp_page_test.js` 抓出的**三个真实 bug**（都在上传前修掉）：

1. **`mqttws.js` 漏拆 `{ data }` 外壳**。小程序 `SocketTask.onMessage` 回调收到的是
   `{ data: ... }`，而 Node 的 WebSocket 直接给数据。第一版只按后者写，
   真机上会表现为**帧收到了却一直不解析、"连接中"卡住**。
   （这是 Node 侧单测测不到的 —— 因为 Node 的 socket 适配器恰好走的是另一种形态。）
2. **降级后通道被标成"警告"**。轮询明明可用却显示警告，自相矛盾。
   改为：等级只反映"健不健康"，"这是降级来的"只体现在文案里。
3. **降级原因缺行动指引**。原来只写原始错误码，现在直接给出"去 socket 合法域名加 `wss://bemfa.com`"。

> 顺带踩到一个 JS 陷阱：`page.stopChannel()` 后面紧跟以 `[` 开头的一行时，
> 会被解析成"给上一行返回值取下标"。测试脚本里已加注释说明。
