# 07 · 联网反复断连（断了又连、连了又断）排查与修复

适用现象：ESP01S 能连上热点、也能发出数据，但运行一会儿就掉线，自动重连后又掉，
在串口日志上表现为循环出现 `[NET] connected` → `[NET] publish failed` /
`[NET] ping failed`。

---

## 一、先看结论：这次为什么断

排查后确认有两层原因，**代码层那一层是确定性的缺陷**，不是"信号不好"。

### 根因 1（代码层，主因）：串口接收被 HAL 永久关掉，固件没有恢复

链路是这样断的：

1. `DHT11` / `DS18B20` 的单总线时序精度要求高，驱动里用
   `taskENTER_CRITICAL()` 保护（见 `dht11.c` / `ds18b20.c`）。
2. 在 Cortex-M3 上，`taskENTER_CRITICAL()` 是靠抬高 `BASEPRI` 实现的，它屏蔽的是
   **优先级数值 ≥ `configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY`（本工程 = 5）** 的中断。
3. 而 `USART1`（ESP01S）的中断优先级恰好就是 **5** —— 也就是说，
   在 DHT11/DS18B20 的临界区里，**ESP01S 的串口接收中断是被压住的**。
4. 这几个毫秒里，如果 ESP01S 正在连续回数据（`WIFI CONNECTED` / `OK` /
   `SEND OK` 都是连发多字节），而 STM32F1 的 USART 只有 1 个字节的接收寄存器，
   后面的字节到达就直接置位 **ORE（溢出错误）**。
5. STM32 HAL 一旦看到 ORE，会执行 `UART_EndRxTransfer()`：**关掉 RXNE/PE/ERR 中断**
   并把 `RxState` 复位，然后才回调 `HAL_UART_ErrorCallback()`。
   **如果固件不接管这个回调，串口接收就永久停摆。**
6. 接收停摆后，后面所有"等 `OK` / 等 `>` / 等 `SEND OK`"必然超时
   → 上层判定发布失败 → 断开重连 → 连上后过一会儿又撞上 → 再断。

**这一条可以完美解释"连得上、但一定会反复断"**：连上之后 DHT11 每 2s 读一次、
DS18B20 每 1s 读一次，临界区一直在周期性出现，撞上 ESP 回数据只是时间问题。

### 根因 2（策略层）：把一次抖动放大成一次完整断连

原实现只要 `MQTT_Publish()` 返回非 0 就立刻 `CIPCLOSE` + 报警 + 重连。
而一次 `CIPSEND` 没等到 `SEND OK`，很多时候**只是链路瞬时拥塞，连接其实还在**。
于是"偶发发送超时"被升级成"完整断连-重连"，并且每次都会让蜂鸣器响 5 秒，
现场感受就是"断了又连、连了又断，还一直叫"。

## 二、这次改了哪些代码

| # | 文件 | 改动 | 解决什么 |
|---|------|------|----------|
| 1 | `user/Src/main.c` | 新增 `HAL_UART_ErrorCallback()` → 转发 `ESP01S_OnError()` | **根因 1 的关键**：出错后重新武装接收，不再永久停摆 |
| 2 | `user/Src/esp01s.c` | 新增 `ESP01S_OnError()`：清 PE/FE/NE/ORE 标志并重挂接收 | 同上 |
| 3 | `user/Src/esp01s.c` | 新增 `ESP01S_RxWatchdog()`：发现没挂着接收就补挂 | 兜底，防止任何遗漏路径导致接收停摆 |
| 4 | `user/Src/esp01s.c` | `ESP01S_RxCplt()` 检查重武装返回值；新增诊断计数 | 让故障可见，不再"静默死掉" |
| 5 | `user/Inc/esp01s.h` | 接收环形缓冲 512 → 1024 字节 | `AT+CWJAP` 阶段数据量大，512 有被写满的风险 |
| 6 | `user/Src/esp01s.c` | `ATCheck` 增加 `AT+CWAUTOCONN=0`、`AT+SLEEP=0` | 禁止模块自行重连抢串口；关闭省电休眠（省电会周期性掉线） |
| 7 | `user/Src/esp01s.c` | `ATCheck` 的 `AT` 握手重试 3 次；`JoinAP` 失败先 `CWQAP` 再重试 | 上电瞬间误判失败；半连接状态导致第二次 `CWJAP` 直接报错 |
| 8 | `user/Src/esp01s.c` | `TcpConnect` 前先 `AT+CIPCLOSE` | 避免 `ALREADY CONNECTED` 造成的"假连接" |
| 9 | `user/Src/esp01s.c` | `TcpSend` 等 `>` / `SEND OK` 时同步识别 `ERROR` / `SEND FAIL` / `link is not valid` | 不白等满超时，并返回可区分的错误码 |
| 10 | `user/Src/app_tasks.c` | publish 失败先**原地重试** `NET_PUB_RETRY_MAX` 次，只有驱动判定链路不可用才放弃 | 解决根因 2 |
| 11 | `user/Src/app_tasks.c` | 重连退避：5s 起翻倍，60s 封顶 | 避免密集重连 |
| 12 | `user/Src/app_tasks.c` | 连续失败达 `NET_ALARM_AFTER_FAILS` 次才鸣蜂鸣器 | 蜂鸣器降噪 |
| 13 | `user/Src/app_tasks.c` | 每轮都调 `ESP01S_Poll()` + `ESP01S_RxWatchdog()`，并同步 `connected` | 不再拿着死连接去发；SOS 路径也受保护 |
| 14 | `user/Src/app_tasks.c` | SOS 报文发布失败**挂起补发**，不丢弃 | 紧急事件不丢 |
| 15 | `user/Src/app_tasks.c` | 补上 `post_alarm()` 的 urgent 唤醒（原来只有 ISR 版会唤醒） | 见下方"顺带修掉的一个需求未落实问题" |
| 16 | `user/Inc/user_config.h` | `MQTT_KEEPALIVE_S` 60 → 30；新增 `NET_*` 策略参数 | 对中间设备 NAT 回收更宽容 |

### 顺带修掉的一个需求未落实问题

原来 `post_alarm()` 只是把 `urgent` 存进事件结构，**并不会唤醒 WiFi_Task**；
只有 ISR 版（`APP_PostAlarmFromISR`）才会 give 信号量。
结果是"**摔倒了要立即上报**"这条需求实际退化成"等下一个 30s 周期"。

现在补上了唤醒，并且用 `s_immediate_report` 区分报文类型：

- 摔倒等 urgent 事件 → 发**数据报文**（带加速度、心率、`status: "FALL ALARM"`）
- SOS 按键（ISR） → 发 **SOS 事件报文**（只有时间与配置的工点坐标）

`ALARM_WIFI_FAIL` 的 urgent 改回 0 —— 它本来就是这个任务自己报的，唤醒自己没有意义。

## 三、烧录后怎么判断还有没有问题

打开串口助手连 **USART2（PA2/PA3，115200-8N1）**，关注这几行：

```
[NET] connect failed step=1 streak=2 wait=10000ms
[NET] connected
[NET] publish failed step=5 tries=3
[NET] ping failed
[NET] uart: ovf=0 rstrt=0 err=0
```

### `[NET] uart: ovf=.. rstrt=.. err=..`（最重要的一行）

这行**只在计数变化时**才打印，所以：

- **一直不出现** → 串口链路健康，说明本地接收侧没问题。
  如果这时仍会断，问题在下一节的"网络 / 硬件"层。
- **`err=` 在涨** → 就是本文描述的 ORE 场景。修复后接收能自愈，
  但**计数持续快速增长本身不理想**，见下面的"进一步降低 ORE 频率"。
- **`ovf=` 在涨** → 环形缓冲被写满，说明任务侧消费不及时，
  可再把 `ESP_RXBUF_SIZE` 调大。
- **`rstrt=` 在涨** → 接收确实掉过、被看门狗救回来了（这是兜底生效的证据）。

### 失败步骤号对照（`connect failed step=N`）

| step | 失败环节 | 优先检查 |
|------|----------|----------|
| 1 | `AT` 握手 / `CWMODE` | 波特率（115200 还是 9600）、TX/RX 是否接反、模块供电 |
| 2 | `AT+CWJAP` 连热点 | 热点是否 2.4GHz、密码、SSID 大小写、热点是否允许新设备 |
| 3 | `AT+CIPSTART` 建 TCP | DNS/网络出口、`bemfa.com:9501` 是否可达 |
| 4 | MQTT CONNECT（等 CONNACK） | 私钥是否正确、**同一私钥是否已被别处占用** |

## 四、网络 / 硬件层检查清单（按嫌疑排序）

代码修完之后如果仍断，按这个顺序查：

1. **ESP01S 的供电（头号嫌疑）**
   ESP8266 发射瞬间电流可达 300mA 以上。若从 STM32 最小系统板的 3.3V 引脚
   或 USB-TTL 的 3.3V 取电，极容易因压降复位，表现就是"连上几十秒、
   然后掉、重连、又掉"。
   → 用独立 3.3V LDO（≥500mA，如 AMS1117-3.3），并在模块 VCC-GND 就近
     并 **100µF 电解 + 0.1µF 瓷片**。这是最值得先做的一件事。

2. **手机热点必须是 2.4GHz**
   ESP01S 不支持 5GHz。多数手机默认"5GHz 优先"或"双频合一"，
   在这两种模式下 ESP01S 会搜不到或连不稳。
   → 在热点设置里显式选 2.4GHz 频段。另外关掉热点的"智能省电/自动关闭"。

3. **同一私钥被别处占用（会互相踢）**
   巴法云同一私钥只允许一个连接。若同时用 MQTTX / 巴法云 App 调试，
   或**旧工程 `stm32-dht11-cloud` 也在用同一个 `BEMFA_UID` 并且也在跑**，
   两者会反复互踢 —— 这是"断了又连"的经典成因。
   → 调试时给设备单独用一个私钥，或确保只有一个客户端在线。

4. **主题是否存在**
   `BEMFA_TOPIC`（`temp001`）必须已在巴法云控制台建好，否则发布会被拒。

5. **天线与距离**
   ESP01S 是板载 PCB 天线，贴着金属、被手遮挡、或离手机太远都会明显掉线。

### 进一步降低 ORE 频率（可选，进阶）

本工程选择了"保持 USART1 优先级 = 5，出错即自愈"的折中方案，
原因见 `main.c` 中 `USART1_IRQn` 优先级处的注释：
把它提到 4（高于 FreeRTOS 临界区屏蔽线）虽然能基本消除 ORE，
但串口中断会插进 DHT11/DS18B20 的微秒级时序，反过来打乱位判读。

如果实测 `err=` 增长过快、影响体验，两个更彻底的方案（按推荐度）：

- **接收改 DMA 循环模式**：DMA 在硬件层面持续搬数据，CPU 关中断不影响，
  从根上消除 ORE，也不干扰单总线时序。代价是需要重写接收侧索引管理。
- **把 DHT11/DS18B20 的读取安排在 WiFi 空闲窗口**：改动小但耦合较高，不推荐。
