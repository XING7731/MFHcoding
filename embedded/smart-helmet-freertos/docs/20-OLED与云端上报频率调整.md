# 20 — OLED 刷新与云端上报频率调高

> 需求原话："数据上传 oled，云平台频率调高一点"
>
> 落地方式：**只改两个宏 + 一处打印阈值**，任务逻辑零改动，编译 0 Error / 0 Warning。

---

## 1. 改动清单

| 文件 | 位置 | 原值 | 新值 | 倍数 |
|------|------|------|------|------|
| `user/Inc/user_config.h` | `DISPLAY_PERIOD_MS` | 2000 | **500** | 4x |
| `user/Inc/user_config.h` | `UPLOAD_PERIOD_MS` | 30000 | **10000** | 3x |
| `user/Src/app_tasks.c` | DisplayTask 内 `stack_tick >=` | 5 | **20** | 抵消周期变化，维持"约 10s 打一次栈水位" |

编译结果：**0 Error, 0 Warning**，`Code=38950 RO-data=1466 RW-data=344 ZI-data=17016`。
烧录文件：`MDK-ARM/smart-helmet-freertos/smart-helmet-freertos.hex`（113803 B）。

---

## 2. 为什么取这两个值 —— 先算清时间预算

### 2.1 OLED：500ms（I2C1 时间账）

| 项 | 数值 |
|----|------|
| 显存容量 | 128 × 64 / 8 = **1024 B** |
| 每字节线上开销 | 9 bit（8 数据 + 1 ACK）+ 从机地址/控制字 |
| I2C1 速率 | 400 kHz |
| **整屏写一帧耗时** | **约 25~30 ms** |

于是各周期的总线占空比：

| DISPLAY_PERIOD_MS | 单帧耗时 | 占 I2C1 带宽 | 评价 |
|---|---|---|---|
| 2000（原值） | ~30 ms | 1.5% | 太保守，屏幕看起来"卡" |
| **500（现值）** | ~30 ms | **约 6%** | 流畅，余量充足 |
| 200 | ~30 ms | 约 15% | 仍可用，是安全下限 |
| 100 | ~30 ms | 约 30% | **不建议**：单帧持锁 30ms，接近 Sensor_Task 取锁超时 50ms |

关键前提：`Display_Task` 优先级 **0（最低）**，它持 I2C 锁时若 Sensor_Task（P=1）
醒来，互斥量的优先级继承会让 Display 临时提级并尽快释放，Sensor 等待时间
≈ 单帧耗时 30ms < 取锁超时 50ms，**不会丢 MAX30102 采样**。
但这条余量只有 20ms，所以周期不宜再往 100ms 压。

### 2.2 云端：10s（上报轮次账）

WiFi_Task 一轮的构成为：

```
等信号量(超时 UPLOAD_PERIOD_MS) → ESP01S_Poll → 组 JSON → PUBLISH(最多 NET_PUB_RETRY_MAX 次重试)
                                → net_confirm_echo(最长 NET_ECHO_TIMEOUT_MS = 4000 ms)
                                → 心跳检查
```

| 阶段 | 正常耗时 | 最坏 |
|------|---------|------|
| 发布（CIPSEND + SEND OK） | 约 0.5~1 s | 重试后约 2 s |
| 回环确认（等 Broker 把报文推回来） | 约 0.1~0.5 s | **4 s（超时）** |

- 10s 周期：正常一轮约 1~2s，**留 8s 余量**，绝不会出现"上一轮没走完下一轮又被拉起"。
- 若压到 5s：最坏情况（echo 超时 4s + 发布 2s = 6s）**会打不住**，不建议低于 5s。
- 报文长度：紧凑格式约 **147 B < 191 B**（巴法云记录字段上限，见 docs/18），
  所以每条都会真正落库，不会再出现"控制台看不到"。
- 速率：10s 一条 ≈ **6 条/分钟**，远低于巴法云任何限流阈值。

## 3. 副作用与已核对项

| 项 | 结论 |
|----|------|
| 栈水位打印频率 | 原本"每 5 个显示周期 ≈ 10s"打印一次；周期变 4 倍后会变 2.5s 一次 → **阈值 5 → 20 抵消**，串口日志量不变 |
| MQTT 心跳 | `MQTT_KEEPALIVE_S` 保持 30；WiFi_Task 每 10s 检查一次 `≥ 15s` 判据，实际约 20s 发一次 PINGREQ，仍小于 keepalive，安全 |
| OLED 报警响应 | AlarmTask 写快照 → Display 刷新，报警文案上屏延迟从 ≤2s 降到 **≤0.5s**（变好） |
| SOS 立即上报 | 走信号量抢发，不受周期影响，行为不变 |
| 传感器采样 | `SAMPLE_PERIOD_MS=100`、`DHT11_PERIOD_MS=2000`、`DS18B20_PERIOD_MS=1000` **均未改动** |
| 数据新鲜度 | OLED 显示值每 500ms 更新一次；云端每 10s 一条 |

---

## 4. 想再快怎么改

只动 `user_config.h` 的两个宏即可，逻辑无需改：

```c
#define DISPLAY_PERIOD_MS     200    /* OLED 安全下限，占 I2C1 约 15% */
#define UPLOAD_PERIOD_MS      5000   /* 云端安全下限，2x 于最坏单轮耗时 */
```

**不要**把 `DISPLAY_PERIOD_MS` 压到 100ms 以下：单帧仍要 30ms，
会显著挤占 I2C1 上 MAX30102 的 FIFO 读取窗口。

### 验证办法

1. 屏幕第 8 行联网诊断行的 `p`（发送成功次数）/`e`（回环确认次数）计数——
   改为 10s 周期后，两个数**约 10 秒涨 1**，且 `p ≈ e`。
2. 电脑侧 `tools/bemfa_tap.py` 订阅监听，看 `seq` 的递增间隔是否约 10s。
3. 巴法云控制台"记录"里，`time` 字段的刷新间隔应由 30s 变为约 10s
   （注意平台侧 `time` 有 1~2 分钟延迟，判新旧仍以 `seq` 为准）。
