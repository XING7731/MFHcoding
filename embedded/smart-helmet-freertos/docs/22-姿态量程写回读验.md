# 22 · 姿态量程写回读验（MPU6050 加速度量程自检）

> 本版固件新增：**写完 `ACCEL_CONFIG` 立刻读回核对**，并按读回值决定换算系数。
> 目的只有一个 —— 让"量程到底写进芯片了没有"这件事，由固件自己给出证据，
> 而不是靠代码里"我写了，所以它应该是"的假设。

---

## 1. 起因：静止时合加速度是 3.95g

用云端接口抓板子真实报文时发现：

```
ax = 3.9,  ay = 0.2,  az = 0.6
|a| = √(3.9² + 0.2² + 0.6²) ≈ 3.95 g
```

连续两次探测（间隔 10 秒）**完全一致**，不是抖动，是稳定偏置。
静止时合加速度必须是 **1.0g**（只有重力）—— 所以这里差了约 **4 倍**。

## 2. 根因推导：差 4 倍 = 量程档位差两级

```
3.95 ÷ 4 = 0.988 ≈ 1.0 g          ← 恰好是 1g
```

而 4 这个倍数不是巧合，它正好是相邻量程档的灵敏度比：

| 量程 | AFS_SEL | ACCEL_CONFIG | 灵敏度 |
|---|---|---|---|
| ±2g | 0 | `0x00` | **16384** LSB/g |
| ±4g | 1 | `0x08` | 8192 LSB/g |
| ±8g | 2 | `0x10` | **4096** LSB/g |
| ±16g | 3 | `0x18` | 2048 LSB/g |

```
16384(±2g) ÷ 4096(±8g) = 4
```

**结论**：配置按 ±8g 写入（`ACCEL_CONFIG = 0x10`），驱动按 4096 LSB/g 换算，
但芯片实际停在寄存器复位的 **±2g 默认档**（应该用 16384 LSB/g 换算）。
读数因此被整体放大了 4 倍。

> 市售 GY-521 模块使用克隆芯片时，量程寄存器写入不生效是常见故障。
> 原代码里三个 `reg_write()` 的返回值**全程未被检查**，所以"写进去没有"
> 固件自己也不知道 —— 读数是错的，但没有任何地方会报错。

## 3. 为什么这个失效比"数值不准"严重得多

摔倒判据是一个三条件状态机（`fall_detect.c`）：

```
① |a| > FALL_ACCEL_HIGH_G (2.5g)
② 100ms 内再次超过阈值
③ 随后 1.5s 内持续 < FALL_ACCEL_LOW_G (1.5g)
```

偏置把 `|a|` 常年顶在 3.95g：

- 条件① **恒满足**（真摔假摔都满足，失去筛选意义）
- 条件③ **永不满足**（|a| 从不低于 1.5g）

→ **真摔也不会报警**。而屏幕上一切正常：`st=normal`、数值不断跳动、
上报链路全程通畅。这是最难发现的一类失效 —— **功能没了，却没有任何提示**。

## 4. 本版做了什么（三层）

### 第 1 层：写 → 读回 → 核对 → 重试

`mpu6050.c` 新增 `reg_write_verify()`：

```c
for (i = 0; i < MPU6050_WRITE_RETRY_MAX; i++) {   /* 默认 3 次 */
    reg_write(reg, val);
    HAL_Delay(2);                                  /* 留出寄存器更新时间 */
    if (reg_read(reg, &rd, 1) == 0) {
        if (rd == val) return rd;                  /* 一致 → 通过 */
        got = rd;
    }
}
return got;                                        /* 不一致 → 交出实际值 */
```

重试之间隔 2ms：克隆片多为"第一次写不进、第二次就好"，同时也避免
"写进去了但立刻读回还是旧值"被误判为失败。

### 第 2 层：换算系数按【读回值】决定，而不是按编译期配置

```c
cfg_rd = reg_write_verify(MPU_REG_ACCEL_CONFIG, cfg_wr, &retry);
fs_got = afs_to_fs_g(cfg_rd);              /* 只取 bit4:3 的 AFS_SEL */
s_accel_lsb_per_g = fs_g_to_lsb(fs_got);   /* ← 关键: 用实际档位换算 */
```

这一层的意义：**把问题从"数值错但看不出来"降级为"数值对 + 一条明确告警"**。
无论芯片最终落在哪一档，报出来的 g 值都是对的。
`afs_to_fs_g()` 只解析 `AFS_SEL` 两位，忽略寄存器里 HPF 等其它位，
所以别的位有差异也不影响判读。

### 第 3 层：修不了的部分，就让它显眼

若实际量程 **≤** 摔倒阈值（如 ±2g ≤ 2.5g），冲击被削顶在 2g，
判据在**物理上**不可能触发 —— 这靠软件补不回来。

此时 `SelfCheck.fatal = 1`，固件做两件事：

1. 上电自检屏第 7 页直接给出**可照抄的宏值**：`FIX FS_G=2 FALL 1.8`
2. 运行期间把屏幕第 6 行让给常驻告警：`! FALL DET DISABLED`

> **为什么固件不自动把阈值降下来**：降阈值属于**检测策略变更**，
> 会改变灵敏度与误报率。这种决定必须由人做，固件只负责把事实摆出来。

## 5. 看屏判读

### 5.1 上电自检屏（停留约 3.5 秒）

```
SMART HELMET
I2C1 PB6/7: 3C 57
I2C2 PB10/11: 68
O:OK M:OK X:OK
MAX30102 OK
MPU 1C w10 r10          ← 寄存器级证据: w=写入值, r=读回值
MPU FS 8g->8g OK        ← 翻译成 g: 想要 8g, 实际 8g
```

| 第 6 页 | 第 7 页 | 含义 | 处理 |
|---|---|---|---|
| `MPU FS 8g->8g OK` | 不显示 | 量程按预期生效 | 无需处理 |
| `MPU FS 8g->4g !` | `FIX FS_G=4` | 芯片锁在 ±4g。**读数已自动修正**，且 4g > 2.5g，判据仍有效 | 把 `MPU6050_ACCEL_FS_G` 改成 4 消除告警 |
| `MPU FS 8g->2g !!` | `FIX FS_G=2 FALL 1.8` | 芯片锁在 ±2g，**判据无法触发**（fatal） | 见第 6 节 |
| `MPU6050 err rc=2` | — | WHO_AM_I 不是 0x68，芯片没打通 | 查接线/供电/AD0 电平 |

标记含义：`OK` = 实际量程与配置一致；`!` = 不一致但不致命；`!!` = **致命（摔倒判据已失效）**。

> `FIX` 那行的文案针对最常见的 ±2g 锁定场景（顺带提示要一起降摔倒阈值）。
> **通用规则只有一句**：`MPU6050_ACCEL_FS_G` 填第 6 页箭头右边的数（实际量程），
> `FALL_ACCEL_HIGH_G` 必须**小于**它 —— 否则冲击削顶，判据不可能触发。

> **判据用的是"解出的量程"，不是"寄存器字节是否逐位相等"。**
> 若读回值与写入值不同、但 `AFS_SEL` 解出来是同一档（例如 `w10 r11`），
> 差异在 HPF 等无关位上，量程其实是对的 —— 这时第 6 页仍显示 `OK`、
> 第 7 页不出现。原始字节差异在第 5 页 `w.. r..` 里如实保留，
> 需要细看时能看到，但不会误导你去改一个本来不用改的宏。

### 5.2 运行时屏幕（第 6 行 / page 5）

正常情况下这行显示 `STATUS: normal` 或 PPG 调试行。**只有异常时才被占用**：

| 显示 | 含义 |
|---|---|
| `! MPU6050 FAIL` | `MPU6050_Init()` 返回非 0 —— 芯片读不到 |
| `! FALL DET DISABLED` | 量程削顶在阈值以下 —— 真摔不会报警 |

告警行优先级排在 **PPG 调试行之前**：PPG 行只是排查辅助，
而这一条关系到安全功能是否还在工作。

如果不想看到它，把 `user_config.h` 的 `MPU6050_FS_ALERT_LINE` 改成 0。

### 5.3 USART2 日志

```
[BOOT] MPU WHO=0x68 1C wr=0x10 rd=0x10 retry=0
[BOOT] accel FS want 8g == got 8g, scale OK
```

异常时：

```
[BOOT] MPU WHO=0x68 1C wr=0x10 rd=0x00 retry=3      ← 写了 3 次都读回 0x00
[BOOT] accel FS MISMATCH want 8g got 2g
[BOOT] scale re-derived from readback -> set FS_G=2  ← 换算系数已自动修正
[BOOT] !! actual FS <= fall threshold: fall detect CANNOT fire
[BOOT] !! fix: MPU6050_ACCEL_FS_G=2, FALL_ACCEL_HIGH_G=2.5, FALL_ACCEL_LOW_G=1.5
```

`retry` 字段很有用：`retry=0` 表示一次就写成（芯片正常只是档位不同），
`retry=3` 表示反复写不进（克隆片行为，或总线信号质量差）。

## 6. 处理步骤（针对 ±2g 锁定的情况）

1. 先确认换算已自动修正：板子**平放桌面静止**，看第 5 页加速度行
   `A:x.x y.y z.z` —— 应该显示约 `1.0g`，而不是之前的 `3.9g`。
   **这一步是分水岭**，见第 7 节。
2. 改两个宏（`user/Inc/user_config.h`）：

   ```c
   #define MPU6050_ACCEL_FS_G    2      /* 从 8 改为 2: 与芯片实际档位一致 */
   #define FALL_ACCEL_HIGH_G     1.8f   /* 从 2.5 改为 1.8: 必须 < 量程上限 2g */
   ```

   > **为什么阈值必须一起改**：±2g 档下 |a| 饱和在 2g，2.5g 的判据永远
   > 达不到（这正是 `fatal` 判据的来源）。降到 1.8g 才落在可测范围内，
   > 且仍高于 1g 静止值和 1.5g 的 `FALL_ACCEL_LOW_G`，两个条件不会打架。
3. 重新编译烧录，确认自检屏变成 `MPU FS 2g->2g OK`、运行时不出现告警行。
4. 若换了新模块，芯片是正品 ±8g，把这两个宏改回 `8` / `2.5f` 即可。

## 7. 一个重要的交叉验证（判断"读回"本身可不可信）

自动修正换算系数有个前提：**读回值是可信的**。若总线质量问题导致读回
失败（返回 0），固件会误判成 ±2g、进而用 16384 换算 —— 反而把正确的
±8g 读数缩小了 4 倍。

**区分方法就是静止时的 |a|**：

| 静止 |a| 显示 | 说明 | 结论 |
|---|---|---|---|
| ≈ **1.0g** | 读回值可信，芯片确实在 ±2g | 按第 6 节改宏 |
| ≈ **0.25g** | 读回值不可信，芯片其实在 ±8g | 是总线/读回问题，别改宏；查 I2C 上拉与走线 |
| ≈ 4.0g | 既没读回成功、换算也没修正 | 异常，上报日志 |

`0.25 = 1.0 ÷ 4`，与 `3.95 = 0.99 × 4` 是同一倍数关系的两个方向。

## 9. 2026-09-16 更正：还有第三种情况，读回值本身就在说谎

本文第 1~8 节的前提是"读回值可信"。**现场实测推翻了它。**

手上这颗克隆片的表现是：

```
[BOOT] MPU WHO=0x68 1C wr=0x10 rd=0x10 retry=0
[BOOT] accel FS want 8g == got 8g, scale OK      ← 全绿
静止 |a| = 3.9g                                   ← 但读数放大 4 倍
```

寄存器能写能读回、读回来就是 ±8g，`fs_match = 1`、`fatal = 0`，
自检屏无告警、运行时也不显示 `! FALL DET DISABLED` —— 而芯片内部灵敏度
仍然锁在 ±2g。**驱动按读回值自适应换算这个"优点"，在这颗片子上反而
把错误读数的最后一层防护也堵住了。**

### 9.1 本文第 7 节的判据表要加一行

| 静止 \|a\| 显示 | 说明 | 结论 |
|---|---|---|
| ≈ 1.0g | 读回值可信，芯片确实在 ±2g | 按第 6 节改宏 |
| ≈ 0.25g | 读回值不可信，芯片其实在 ±8g | 查 I2C 上拉与走线，别改宏 |
| ≈ 4.0g | 既没读回成功、换算也没修正 | 异常，上报日志 |
| **≈ 3.9g 且自检显示 `8g->8g OK`** | **← 本次新增**：读回值被伪造成 ±8g，实际锁 ±2g | 走 `docs/25`，别按第 6 节改 |

### 9.2 处理方式变了

第 6 节建议的 `FALL_ACCEL_HIGH_G = 1.8` 只适用于"读回值 = 2g"的情况。
本次这种"读回值 = 8g 但实际 2g"的片子，**不能改 `MPU6050_ACCEL_FS_G`**
（改了读回值还是 8，换算还是 4096，毫无作用），只能：

- **短期**：把判定阈值一并放大到同一读数体系 ——
  `FALL_ACCEL_HIGH_G = 5.0f` / `FALL_ACCEL_LOW_G = 4.5f`（已执行）；
- **彻底**：按 16384 LSB/g 强制换算，让读数回到真实 g。

两条路的完整取舍见 **`docs/25-摔倒阈值调整与克隆片读数放大.md`**。

### 9.3 本文第 9 节（原"一句话总结"）的补充

> 比"写进去了没生效"更隐蔽的是"读回来说生效了、其实没生效"。
> 寄存器是芯片自己报的，芯片可以报错、可以沉默，也可以**撒谎**。
> 最终能当裁判的只有一个东西：**物理常识** —— 静止物体的合加速度
> 必须是 1.0g，无论寄存器怎么说。

## 10. 一句话总结

> 量程是**编译器看不见、运行时必须读回才能确认**的参数。
> 写进去了不代表生效了；不生效也不会报错 —— 只会让一个安全功能
> 安安静静地失效。本版把它变成一件**上电 3.5 秒内就能看见**的事。
