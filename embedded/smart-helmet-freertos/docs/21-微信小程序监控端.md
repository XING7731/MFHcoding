# 21 — 微信小程序监控端（从巴法云读取并显示）

> 需求："根据我的项目功能给我做个微信小程序，实现从我的巴法云获取信息在小程序上显示"
>
> 交付位置：`C:\Users\27362\Desktop\WeChat smart helmet`
>
> 本文记录方案选型、接口实测结论、验证证据，以及**顺带发现的 MPU6050 读数异常**
> （可能导致摔倒检测静默失效，见第 6 节，建议优先处理）。

## 1. 方案选型：小程序只能轮询 HTTP，不能连 MQTT

| 方案 | 可行性 | 原因 |
|---|---|---|
| 小程序直连 `bemfa.com:9501` 跑 MQTT | ✗ | 小程序没有裸 TCP socket，只有 `wx.request`(HTTPS) / `wx.connectSocket`(WSS) |
| 小程序连 WSS | ✗ | 巴法云未提供对外的 WSS 接入 |
| **HTTP 轮询平台查询接口** | **✓ 采用** | 平台提供 HTTPS 查询接口，返回该主题最新一条消息 |

链路：

```
STM32 安全帽 ──MQTT(10s 一条)──▶ 巴法云主题 ──HTTPS 轮询(5s)──▶ 小程序
```

板子上报 10s 一条，小程序取 5s 轮询：既不会漏新数据，也不会做无意义的重复请求。

## 2. 接口实测（`tools/wxmp_api_probe.py`，2026-09-16）

| 候选接口 | 结果 |
|---|---|
| `https://apis.bemfa.com/va/getmsg?uid=…&topic=…&type=1&num=1` | ✅ **采用**。返回最干净：`{"code":0,"message":"OK","data":[{"msg":"…","time":"…","unix":1789522050}]}` |
| `https://apis.bemfa.com/vb/api/v2/allTopic?openID=…&type=1` | ✅ 可用，多返回 `online`/`pubOnline`/设备名/`unix`，但需要遍历主题列表 |
| `https://api.bemfa.com/api/device/v1/data/1/get/` | ✗ `{"code":"40012","status":"topic error"}`，该路径不适用于本私钥 |
| `getmsg` 带 `num>1` 想取历史 | ✗ 返回 `data:null` —— **该接口只给最新一条，历史拿不到** |

**两个结论直接决定了小程序的设计：**

1. **要 HTTPS**：`apis.bemfa.com` 支持 HTTPS，所以小程序能调；但必须把它加进
   微信公众平台的 **request 合法域名**，否则真机直接失败。
2. **拿不到历史**：趋势图与报警记录只能由小程序**本机缓存**攒出来。

### 顺手验证到的事：新固件（10s 周期）确实在跑

两次探测之间拿到：

| 次 | `seq` | `up` | 时间 |
|---|---|---|---|
| 第 1 次 | 13 | 137977 | 10:02:18 |
| 第 2 次 | 14 | 148245 | 10:02:28 |

`up` 相差 **10268 ms**，`seq` +1 ⇒ 与"10 秒上报一次"完全吻合，
即 `UPLOAD_PERIOD_MS = 10000` 的固件已在稳定运行（对照 docs/20）。

## 4. 三个关键设计点（都是本项目踩过的坑）

### 4.1 判"设备死活"用 **云端时间**，不用报文里的 `ts`

板子没有 VBAT 电池，RTC 每次上电回到编译初值。实抓报文里 `ts="10:02:28"`，
而真实时间已是 09:27 —— **差了好几天**（`tsv=0` 就是在如实标注"未校时"）。

所以小程序判在线用的是接口返回的 `unix`（云端接收时刻）：

| 云端时间距今 | 判定 |
|---|---|
| ≤ 30 s | 🟢 设备在线 |
| 31 ~ 90 s | 🟠 数据延迟 N 秒 |
| > 90 s | 🔴 设备已离线（附离线时长） |

> 这与 docs/17 的结论一致：**判新旧只看 `seq`/云端时间，不看 payload 里的时间戳。**

### 4.2 记趋势必须**按 `seq` 去重**

轮询 5s、上报 10s ⇒ 每两条新数据之间会被轮询到两次。
若直接追加，趋势图会出现**重复点**、统计值失真。实现是：只在 `seq` 变化时追加
（见 `bemfa.js` 的 `recordPoint()`），并顺带识别 `seq` 回退（设备重启）。

首页还会把"序号跳变"显示出来：`seq` 跳 +2 以上 ⇒ 中间有报文未落库
（例如超过平台 191 字节上限被丢，见 docs/18）。**这个判据把之前的教训做成了常驻监控。**

### 4.3 心率/血氧的 `null` 与"0"必须区分

`hr:null` 表示"没测到信号"，界面显示 `--` 并说明"未检测到（未佩戴 / 信号不足）"，
绝不显示成 0 —— 否则用户会以为"心率是 0"而去找算法问题（对照 docs/15）。

## 6. ⚠️ 顺带发现：MPU6050 合加速度 3.95g —— 可能导致摔倒检测**静默失效**

这一条与小程序无关，但是本轮用真实数据时暴露出来的，**建议优先处理**。

### 6.1 现象

实抓报文里的三轴加速度（连续两次探测完全一致，说明不是瞬时抖动）：

```
ax = 3.9 g,  ay = 0.2 g,  az = 0.6 g
|a| = √(3.9² + 0.2² + 0.6²) = 3.95 g
```

**静止（或手持）状态下，合加速度应当 ≈ 1.0 g**（重力）。3.95g 不是"板子在动"能解释的
—— 而且注意：

```
3.95 ÷ 4 = 0.988 ≈ 1.0 g   ← 恰好是 1g 的 4 倍
```

### 6.2 推断

`user_config.h` 里 `MPU6050_ACCEL_FS_G = 8`（±8g），驱动据此：

- 写 `ACCEL_CONFIG(0x1C) = 0x10`（AFS_SEL=2，±8g）
- 换算用 **4096 LSB/g**

驱动代码本身是**配对正确**的（`mpu6050.c` 第 62~70 行）。但：

> **`reg_write()` 的返回值全程没有被检查**（第 51~73 行所有写入都忽略返回值），
> 所以"量程到底写进去没有"固件自己也不知道。

若芯片实际仍工作在 **±2g（16384 LSB/g，上电默认档）**，而代码按 **4096** 解码，
读数就会被**放大 4 倍**：真实 1g → 显示 4g。**与实测 3.95g 高度吻合。**

可能原因（按可能性排序）：
1. 市售模块大量使用**克隆/兼容芯片**，`WHO_AM_I` 能返回 0x68，但量程寄存器不生效；
2. `AFS_SEL` 写入因 I2C 时序/上拉问题未成功；
3. 芯片零偏异常（但"恰好多 4 倍"更像换算问题，而非零偏）。

### 6.3 为什么要紧：摔倒检测会**静默失效**

固件的摔倒判据是状态机（`fall_detect.c`）：① `|a| > 2.5g` → ② 100ms 内再次 > 2.5g
→ ③ **随后 1.5s 内持续 < 1.5g** 才判定摔倒。

由于偏置让 `|a|` 恒定在 ≈3.95g，**条件③永远不满足** ⇒
**即使真的摔倒，也不会报警**。而屏幕上一切正常（`st = normal`），
用户不会察觉核心功能已失效。

### 6.4 怎么确认（两步，都不需要额外器材）

**第一步（只看不动手）**：把板子**平放桌面静止**，看小程序首页（或固件 OLED）
的合加速度：

| 观察结果 | 结论 |
|---|---|
| \|a\| ≈ 1.0g | 正常，本轮数据只是当时在动 |
| \|a\| 仍 ≈ 3.9g | **确认异常**，做第二步 |

**第二步（改一个宏，10 秒定性）**：把 `user_config.h` 里

```c
#define MPU6050_ACCEL_FS_G    8      →      #define MPU6050_ACCEL_FS_G    2
```

重新编译烧录后再看：

| 结果 | 结论与后续 |
|---|---|
| \|a\| 变成 ≈ 1.0g | 证明芯片实际锁定在 ±2g 灵敏度（换算放大 4 倍）。**此时必须同时把摔倒门限降到量程内**（`FALL_ACCEL_HIGH_G` 2.5 → 1.6~1.8），否则 ±2g 饱和在 2g，2.5g 判据永远达不到 |
| \|a\| 仍是 ≈ 3.9g | 说明 ±8g 确实生效、芯片真的输出 3.9g ⇒ 转查硬件（芯片真伪 / 焊接 / 供电） |

> 更稳妥的长期做法：在 `MPU6050_Init()` 里写完后**读回 `ACCEL_CONFIG` 并上报**
> （串口打印 + 上电自检屏显示），让固件自己证明量程生效 —— 这比改宏试探更有说服力。

### 6.5 顺带一提：本工程没有 MPU6050 零偏标定

`mpu6050.c` 头注释写明"不做零偏/温漂标定"。静止时三轴应分别接近
`(0, 0, 1g)`，若有明显恒定偏移，也应在初始化时采集若干样本求均值做一次零偏补偿。
