# 16 · 「NET 有数」不等于数据上云 —— 先判定谁占着那条连接

## 一、这一轮的实际观测（2026-09-13 22:55 前后）

用 HTTP 只读接口查该私钥下的全部主题，**采样 45 秒，零变化**：

```
topic      online   pubOnline  time                 msg
temp001    True     False      2026-09-13 22:11:43  {"seq":8702,"source":"echo_verify"}
```

三条信息，每条都很硬：

| 观测 | 含义 |
|---|---|
| `time` 停在 **22:11:43** | 那是电脑脚本发的测试报文。查询时已过去 **40 多分钟**，云端一条新数据都没有 |
| `pubOnline = False`（全程） | 这个主题上**没有任何发布者在线上**。板子每 30 秒在发，却完全不计入 ⇒ 它发的报文**没有到达 Broker** |
| `online = True`（全程不动） | 有一个**只订阅、不发布**的东西**稳定占着**这条连接，且 45 秒内一次都没抖动 |

`online=True` + `pubOnline=False` 这个组合，最像**一个别的客户端正用同一私钥占着唯一那条连接**。
巴法云同一私钥只允许一条 MQTT 连接，谁后到谁被顶，**而 ESP01S 被顶时不会主动报 `CLOSED`** ——
所以板子自己完全不知道，照样一路"发送成功"。

> 注意：`online` 字段本身有约 2 分钟的滞后，**不能单独用它判断板子活没活**。
> 真正实时的是 `time` / `msg`（有没有新数据）和 `pubOnline`。

## 二、为什么「NET 有数」不能当判据

OLED 第 8 行的 `NET:` 里有两种数字，含义完全不同：

| 屏幕 | 含义 | 结论 |
|---|---|---|
| `NET: OK p=12 e=12` | `p` = AT 层发送成功次数，`e` = **回环确认次数**，两个一起涨 | 数据**真的上云了** |
| `NET: OK p=12 e=0` / `NET: p=12 NO ECHO` | 发了 12 次，**一次回环都没收到** | **假成功**，报文没到 Broker |

`p` 来自 `AT+CIPSEND` 的 `SEND OK` —— 那只是 **ESP01S 模块内部**收下了这串字节，
中间还隔着 WiFi、热点 NAT、公网。QoS0 没有 PUBACK，所以**只有回环能证明送达**。

**所以：`NET:` 后面只要有数字就算"网络正常"是错的。必须看有没有 `e`，以及 `e` 会不会涨。**

## 四、心率部分：`d` 和 `a` 都有数，说明什么

PPG 诊断行 `PPG d:58234 a:312`：

- `d` = 红外直流（收到多少光），`a` = 交流峰值（搏动分量多大）

**d 和 a 都非零，说明光路完全打通了**：LED 亮了 → 光穿过手指 → 光电管收到了搏动信号。
**采集环节没有问题**，不需要再查接线、供电、贴合。

那么剩下的就是"算法有没有从这段波形里数出心跳"，看屏幕第 2 行：

| 第 2 行 | 含义 |
|---|---|
| `HR:78 SpO2:--` | 已经出值（SpO2 未标定，所以是 `--`，正常） |
| `HR:-- SpO2:--` 且 `a` 有数 | 有波形但**峰检测没通过** → 手指别动、等 10 秒；仍不出值则需放宽 `PPG_HR_MIN_IBI_MS/MAX_IBI_MS` 或提高 LED 电流 |
| `PPG warming up` | 一个样本都没进来（与本次现象不符） |

**注意：心率读数和云端上报是两条互不相干的链路**，心率读不出来不影响上报，上报发不上去也不影响屏幕显示心率。
不要把它们当成同一个故障。

## 五、一句话总结

> **屏幕上的 `NET: p=N` 只代表 ESP01S 收下了字节，不代表云端收到了。**
> 先看 `e` 涨不涨；`e` 不涨时，用 `bemfa_owner_test.py` 的断电实验判定
> 「是板子的连接死了」还是「连接被别的客户端占着」。
