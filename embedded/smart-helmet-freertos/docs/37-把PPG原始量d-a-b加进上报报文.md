## 二、起因与取证

### 2.1 用户报的现象

"测量 10 次 10 次都失败"，并回答了三问：

- **两处都看**（设备屏 + 小程序）；
- 屏最上面一行是 **`PPG: no pulse, retry`**；
- **已经烧录过 0x4F 新固件**。

### 2.2 云端取证（只读，不占 MQTT 连接）

第一次查：`pubOnline=False`、`online=False`，最新报文停在 **2026-09-21 17:09:08**
（15.7 小时前）⇒ 设备当时断电，那 10 次测量云端一条都没有。
**这条要先排除，否则会把"没数据"误判成"测量失败"。**

第二次查：报文时间 **09:31:11**、`seq=15`、`up=152651ms`(2.5min)、`ps=0`、`hr=null`
⇒ **设备已恢复上报**，可以远程观察。

### 2.3 屏拍照片（决定性）

```
PPG: no pulse, retry
HR:-- SpO2:--
T:31.5C H:55.0%
```

- `UP:00:01:28` ⇒ 刚启动 88 秒（88 秒里能跑 6 轮测量，与"测了 10 次"吻合）；

  直流并带来波动，是"信号/干扰比"的独立恶化项，值得记录；
- **`! MPU6050 FAIL` 把第 6 行占掉了** ⇒ 屏上那个 `d:.. a:.. b:..` 调试行
  **根本不显示**。之前请用户"读 d/a/b"是无效指令 —— 这点事前没预见到。

## 三、根因一：`d` 的钳位陷阱（观测侧，不是算法侧）

```c
static uint16_t clamp_u16(float v) { ... if (v >= 65535.0f) return 65535; ... }
uint16_t HR_GetIrDc(void)    { return clamp_u16(s_band_dc_ir); }   /* ← 上限 65535 */
```

屏上的调试行和**上行报文原先共用这一个函数**。于是：

| 真实红外直流 | 报出来的 `d` |
|---|---|
| 58234（0x24 实测） | 58234 ✔ 未钳位 |
| ≈128000（0x4F 推算） | **65535** ← 被压平 |
| 262143（12bit…… 实为 18bit ADC 满量程） | **65535** ← 完全看不出来 |

**这个陷阱的坏处不是"数字不准"，而是"方向相反"**：越接近甚至超过 ADC 满量程，
报出来的值越是不动。用它判断"电流是不是给大了 / 波形是不是被削平"，会得到
"一切正常"的结论 —— 而真相正好相反。

> **连带更正**：本轮之前曾建议用户"看 `d` 是否顶到 262143"。这是错的 ——
> 屏上永远显示不出大于 65535 的值。262143 是**硬件满量程**，65535 是**软件钳位**。

## 四、根因二：能定病的三个量一个都取不到

`no pulse, retry` 的确切含义：**10 秒窗口内合格 IBI < `PPG_WIN_IBI_MIN`(3)**，
或攒到了但一致占比 < `PPG_WIN_IBI_CONSIST_PCT`(70%)。它的成因有好几种，分开它们
只需要三个数：

| `d` 红外直流 | `a` 峰值幅度 | `b` 合格拍数 | 含义 | 下一步 |
|---|---|---|---|---|
| ≈0 | 0 | 0 | 压根**没采到光** | 查 LED / 窗口遮挡 / 器件 |
| 很大（顶满量程） | ≈0 | 0 | **ADC 饱和**，交流被削光 | 降 LED 电流 |
| 正常 | 0 | 0 | 有光，但**一个搏动峰都没检出** | 光学耦合 / 压力 / 位置 |
| 正常 | 几百 | 0 | 峰检出了，但**每个间隔都被判据拒掉** | 查不应期 / 切迹 / 离群 |
| 正常 | 几百 | 1~2 | 攒到但**不够 3 拍** | 窗口长度 / 信号质量 |
| 正常 | 几百 | ≥3 | 攒够了但**一致占比不够** | 双峰 / 漂移 |

其中 **`a` 的诊断力最强**：它就是 `s_amp_ref`（`HR_GetPeakAmp()`），
**只在 `on_peak()` 里更新**，而 `on_peak()` 只在"严格局部极大值且
`>= max(0.40×s_amp_ref, 30)`"时才被调用。

> ⇒ **`a≈0` 等价于"带通后的交流从头到尾没超过 30 LSB" = 一个峰都没检出。**
> 这一刀把问题切在"寻峰之前"还是"寻峰之后"，比看 `b` 更靠前。

但**这三个量原先只在 OLED 上**，而那一行又被 MPU6050 告警占着（见 §2.3）
⇒ 云端只能看到 `hr=null` + `ps`，三种病因长得一模一样。

## 五、改法

### 5.1 用 `ts`/`tsv` 换 `d`/`a`/`b`

巴法云该主题的记录上限是 **191 字节**，而现状：

| 项 | 字节 |
|---|---|
| 现有报文实测（含 `ts` 17B + `tsv` 8B） | ≈171 |
| `d`+`a`+`b` 最坏情况 | 28 |
| 直接相加 | **≈199 ✗ 超限** |
| 去掉 `ts`+`tsv` 后 | **≈174 ✔** |

**为什么拿这两个换（依据，不是随手挑的）**：

- 板子**没有 VBAT 电池**，RTC 每次上电回到编译初值 ⇒ `ts` 与真实时间差几小时到几天；
- 屏上**早已按用户要求不显示时间**（`app_tasks.c` 行0 改成 PPG 状态）；
- 云端的**接收时间**才是权威值；
- 小程序**明确规定不用它判在线**（`utils/bemfa.js` 的"数据新鲜度"一节）；
- 小程序里 `ts`/`tsv` 只用于设备信息区显示一行，而那一行的文案本来就写着
  "未校时（设备无电池，忽略此时间）"。

### 5.2 `d` 用"未钳位版"，屏上那行为什么不改

报文没有宽度限制，可以报 6 位数；**屏上一行只有 21 字符**，`d:` 从 5 位加长到 6 位
会把后面的 `a/b` 挤掉 —— 而"截断得看起来正常"比不显示更糟
（`app_tasks.c` 里 `ppgbuf` 的注释记过同类教训）。所以屏上保持钳位版，只把报文换掉。

### 5.3 长度隐患与"有内容降级"（既有问题，本轮一并修）

用 `tools/bemfa_compact_payload_check.py --dry` 实测：

| 场景 | 长度 | 判定 |
|---|---|---|
| 典型：测出心率那一次 | 172 | OK（余量 19） |
| 没测出：`hr=null`，`d/a/b` 有值 | 175 | OK（余量 16） |
| 无数据兜底 | 165 | OK（余量 26） |
| **最坏：所有字段最大位数** | **202** | **★ 超限 11** |

**最坏组合长什么样**：`st="fall_detected"`(21B) + `up` 涨到 8 位 +
`ax/ay/az` 都是 ±16g 的 6 字符 + `gas/lux` 满量程 + 温湿度 3 位数 ——
**这几项同时成立的时刻，正是报警那一帧**。

> 🔻 **后续修订（2026-09-22，见 `docs/39`）**：`lux` 字段已删除，最坏值随之
> 降到 **190 字节（余量 1）**，重新回到 191 字节上限以内。下表的 172/175/202
> 是**改动当时**的数值，保留作为记录；当前数值见 `docs/39` 第四节。

> ⇒ **不加保护的话，"最该上传的那一条"反而最可能被云端丢掉**，
> 而现象只是"控制台没数据"，极其难查（同类事故见 docs/18）。
> 注：这个问题**不是本次改动引入的**（改前最坏 199B 同样超）。

**而且固件里本来就有一个 `enforce_payload_limit()`**，超限时降级成
`{"seq":N,"ovf":1}` —— 一条几乎没内容的报文。对普通帧无所谓，
但落到报警帧上，上云的只是一个"发生过溢出"的标记，摔倒状态本身反而没传上去。

**所以本轮加了一道"有内容"的降级**（在 `build_data_json()` 里，早于那个兜底）：
超过 `NET_PAYLOAD_MAX` 就**只丢温湿度/气体**（2026-09-22 前还要丢光照，见 `docs/39`），
保住 `seq/hr/spo2/sc/ps/d/a/b/cv/ax/ay/az/st/up`（约 152 字节）。
两处阈值统一用 `NET_PAYLOAD_MAX`(180)，保证这里降完不会再触发那层兜底。

### 5.4 改动清单

| 文件 | 改动 |
|---|---|
| `user/Src/heart_rate.c` | 新增 `HR_GetIrDcRaw()`（uint32，不钳位）+ 文件头"追加四" |
| `user/Inc/heart_rate.h` | 声明 `HR_GetIrDcRaw()` |
| `user/Src/app_tasks.c` | `build_data_json()`：删 `"ts"`/`"tsv"`、加 `"d"`/`"a"`/`"b"`、加长度降级；参数 `ts`/`ts_valid` 保留但 `(void)` 掉（缩小改动面） |
| `user/Inc/user_config.h` | 更新字段映射表（去掉 ts/tsv，加 sc/ps/cv/d/a/b），报文长度说明 150B→172B |
| `tools/bemfa_compact_payload_check.py` | **修正过期的 FMT**（此前漏了 sc/ps/cv，算出的长度一直偏小）+ 新增 `--dry` 模式（只算长度，不顶掉板子） |
| `tools/_hr_now.py` | 探针字段顺序加 `d/a/b`（ts/tsv 留末尾兼容旧报文） |

## 七、烧录后怎么用（三步）

1. **烧录**新 HEX，等设备联网（屏最后一行 `NET: OK`）；
2. **贴手指测一次**（稳定 3s + 采集 10s ≈ 13 秒），测完可以放开；
3. **不用再念屏**：云端已经能看到 `ps`/`d`/`a`/`b`，
   用只读探针取最新一帧即可（`tools/_hr_now.py`）。

判读就是 §4 那张表。**先看 `d` 与 `a` 的关系**：

- `d` 十几万、`a` 有明显值（几百）⇒ 信号在，问题在判据侧；
- `d` 十几万而 `a≈0` ⇒ **有光没搏动** ⇒ 贴合/压力/位置（加电流无用）；
- `d` 顶到 262143 ⇒ **饱和** ⇒ 把 LED 电流降档（0x24 或 0x34）。

## 八、顺带发现、但本篇不处理的问题

**`! MPU6050 FAIL`** —— 判据是 `MPU6050_GetSelfCheck()->init_rc != 0`，
即**初始化时压根没读到芯片**，全部姿态数据无效。旁证：`A:0.9 0.0 0.0|0.9`
（静止时模值应为 1.0，而 Y/Z 恒为 0）。

**这意味着摔倒检测现在是失效的** —— 比"心率测不出"更关乎安全，
而且它也是"第 6 行被占、看不到 d/a/b"的直接原因。需要单独排查（接线/供电/地址），
不在本篇范围内。
