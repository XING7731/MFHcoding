# 04 调试与验收清单

按顺序做，每一步都能独立验证，避免"一次全接上然后不知道哪坏了"。

## 阶段 0：裸板验证（不接任何外设）

| 步骤 | 操作 | 通过标准 |
|------|------|----------|
| 0.1 | 只烧录、串口接 PA2/PA3 | 上电打印 `===== boot`，OLED 若未接会初始化失败但不影响运行 |
| 0.2 | 用调试器看任务列表（Keil → View → Watch，或加 `vTaskList`） | 能看到 Alarm/DataProc/Sensor/WiFi/Display 五个任务，优先级 3/2/1/1/0 |
| 0.3 | 观察串口输出节奏 | 每 100ms 有采样相关日志（可选），每 10s 有 `[NET]` 日志 |

## 阶段 1：逐个传感器（每次只接一个）

| 传感器 | 测试方法 | 通过标准 | 常见失败原因 |
|--------|----------|----------|--------------|
| MPU6050 | 串口打印 `ax/ay/az`，静止时观察 | 静止时 az ≈ 1.0g（±1g），翻转板子符号变化 | I2C 地址 AD0 未接地（变 0x69）；上拉电阻缺失 |
| OLED | 上电看显示 | 显示 `SMART HELMET` 与数据行 | 地址 0x3C 不对（个别模块 0x3D）；I2C 无上拉 |
| DHT11 | 等 2s 看温度/湿度 | 温度≈室温、湿度随呼吸升高 | 上拉电阻缺失；读取间隔 <1s；供电非 3.3V |
| DS18B20 | 看 `temp_src` 是否为 `DS18B20`（拔掉 DHT11 测试） | 拔 DHT11 后温度仍正常、湿度变 `--` | 4.7K 上拉缺失；引脚未配开漏 |
| MQ-2 | 串口看 `gas_level` | 预热期后数值稳定；用打火机气体（**不点火**）靠近时数值上升 | 未预热；ADC 引脚配错 |
| ~~PT0603~~ | ~~串口看 `light_raw`~~ | **该项已删除**（2026-09-22 光照功能整体移除，见 `docs/39`） | — |
| MAX30102 | 手指轻压传感器看原始 IR 值 | 手指放上后 DC 明显上升，有周期性波动 | 地址 0x57 通信失败；LED 电流过小 |

## 阶段 2：摔倒检测验证（核心功能，必须实测）

因为 Sensor_Task 周期是 100ms（约 10Hz），验证时要**制造两次间隔约 100ms 的强冲击**：

1. **方法 A（推荐）**：把 IMU 固定在硬质小盒里，用手掌**快速拍击两次**
   （间隔约一个"嗒-嗒"的节奏），随后**保持静止 ≥1.5 秒**。
   → 蜂鸣器应响 3 秒，OLED 第 5 行显示 `FALL ALARM`。
2. **方法 B（可控）**：在 `Data_Processing_Task` 里临时加一段"注入测试样本"的代码，
   按 2.5g→2.5g→(低电平序列) 的顺序喂给 `FallDetect_Update()`，验证状态机
   迁移 `IDLE→IMPACT→CONFIRM→REPORT`。这是写论文时最有说服力的验证方式。
3. **反例测试**：
   - 单次轻放（只有一次冲击）→ **不应报警**；
   - 持续摇晃（冲击后一直在 1.5~2.5g 之间晃）→ **不应报警**（稳定窗口不断被重置）；
   - 报警后再拍一次 → 10 秒锁定期内**不应重复报警**。

> 判据回顾（与需求一致）：|a| > 2.5g → 100ms 内再次 > 2.5g → 之后 1.5s 内持续 < 1.5g。

## 阶段 3：报警与显示

| 用例 | 操作 | 通过标准 |
|------|------|----------|
| 气体报警 | 把 `GAS_ALARM_LEVEL` 临时改小（如 5）或对传感器哈气/喷酒精蒸气 | 蜂鸣器断续鸣 2s，OLED 显示 `GAS ALARM` |
| 高温报警 | 用吹风机热风**远距离**吹 DHT11（注意别烫坏） | 显示 `TEMP HIGH` |
| 低温提示 | 把 `TEMP_LOW_X10` 临时改为 300（模拟 30°C 以下算"低温"） | 显示 `TEMP LOW` |
| ~~光照不足~~ | ~~遮住光照传感器~~ | **该项已删除**（同上，光照功能整体移除） |
| SOS 按键 | 按 PA4 按键 | **立即**（<10ms）蜂鸣器响 3s，显示 `SOS ALARM`，且 WiFi_Task 不等 10s 立刻上报一条 SOS 报文 |
| 报警抢占 | 报警期间再触发另一事件 | 新事件立刻接管（时长重新计算），不会排队等待 |

## 阶段 4：联网上报

1. 改 `user_config.h` 的 `WIFI_SSID/WIFI_PASSWORD` 与 `MQTT_BROKER_HOST`。
2. 用 **MQTT 客户端工具**（如 MQTTX / mosquitto_sub）订阅 `helmet/01/data`。
3. 通过标准：
   - 每 30 秒收到一条数据报文；
   - JSON 可被解析（把 `null` 当作缺失值处理）；
   - 拔掉 DHT11 后 `"humidity":null` 且 `"temp_src":"DS18B20"`（容错生效）；
   - 按 SOS 键后立刻收到 `helmet/01/event` 上的 SOS 报文；
   - 拔掉网线/断电热点：串口出现 `[NET] connect failed step=n`，蜂鸣器响 5s
     （需求要求的行为），10s 后重试。

### 报文示例（实际字段顺序）

```json
{"timestamp":"2026-09-11T10:00:00Z","heart_rate":78,"spo2":null,"temp":32.5,
 "humidity":60.0,"gas_level":12,"accel_x":0.1,"accel_y":0.2,
 "accel_z":-1.8,"status":"normal","timestamp_valid":0,"uptime_ms":123456,
 "hr_valid":1,"spo2_valid":0,"temp_valid":1,"humi_valid":1,
 "temp_src":"DHT11"}
```

> 2026-09-22 起 `light` / `light_valid` / `light_raw` 三个字段已随光照功能删除（`docs/39`）。
> 注意这是**完整报文**（`NET_JSON_COMPACT = 0`）的形态；默认的紧凑报文键名更短，
> 见 `docs/18` 与固件 `user_config.h` 的字段映射表。

SOS 报文：

```json
{"event":"SOS","location":"39.9042 N, 116.4074 E","timestamp":"2026-09-11T10:00:00Z",
 "location_source":"configured_fixed"}
```

## 阶段 5：资源与稳定性

| 检查项 | 方法 | 通过标准 |
|--------|------|----------|
| RAM 占用 | Keil 编译后看 `.map` 的 `Total RW Size` | < 20KB，且 < 18KB 更安全 |
| Flash 占用 | `.map` 的 `Total ROM Size` | < 64KB（勾 MicroLIB） |
| 栈水位 | 各任务里加 `uxTaskGetStackHighWaterMark(NULL)` 打印 | 剩余 > 25% 栈空间 |
| 长稳测试 | 连续运行 ≥2 小时 | 无 HardFault、无死机、上报不掉线 |
| 掉线恢复 | 中途关闭路由器 30s 再开 | 自动重连并恢复上报 |
| 队列溢出 | 观察采样丢弃计数 | 长时间为 0 |

## 已知的"预期现象"（别误判为 Bug）

- 未接 ESP01S 或 WiFi 连不上时，**每 30s 左右蜂鸣器响 5 秒** —— 这是需求规定的
  "连接失败 → 蜂鸣器响 5 秒"，属于设计行为。
- 上电前 1 分钟 `gas_level` 无效（MQ-2 预热期）。
- 上电前几秒 `hr` 为 `--`（PPG 预热与窗口未填满。
- `spo2` 恒为 `null` —— **未标定，属预期**，见 03 文档。
- `timestamp` 从上电初值开始，与真实时间有偏差（无校时源）。
