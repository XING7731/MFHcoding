# 25 · 摔倒阈值调整与"克隆片读数放大"问题

> 2026-09-16 · 起因: 现场反馈"姿态判定怎么没动，加速度就已经 3.9 了，且 x 轴加速度一直保持在 3.9"

## 1. 现场现象（用户原话拆解）

| 观察 | 实际含义 |
|---|---|
| `A:3.9 0.0 0.0`，x 轴一直是 3.9 | 板子静止，X 轴正好竖直朝下，重力 1g 全落在 X 轴上 |
| "加速度就已经 3.9 了" | **静止时 1g 被读成 3.9g —— 放大 4 倍**（真实重力 0.98g × 4 = 3.9） |
| "姿态判定怎么没动" | 状态机常年卡在 `IMPACT`，**真正的摔倒永远不会报警** |
| "把加速度阈值调高到 5" | 本次已执行（HIGH 2.5 → 5.0），并且 **必须连带改 LOW**，见第 3 节 |

四行放在一起，指向同一个根因。

## 2. 根因：读回值也会说谎的克隆片

`mpu6050.c` 的写回读验逻辑本身没错，它能挡住"量程没写进去"的片子。但手上这颗
是更麻烦的一种 —— **ACCEL_CONFIG 寄存器能写能读回，读回来还是 ±8g，而芯片内部
模拟前端根本没换挡，灵敏度锁死在复位默认的 ±2g（16384 LSB/g）**。

于是：

```
写 ACCEL_CONFIG = 0x10 (±8g)
读回 ACCEL_CONFIG = 0x10  → fs_match = 1, fatal = 0
驱动据此选 lsb_per_g = 4096   ← 但芯片实际是 16384
                              ↓
真实 1.0g  →  读数 1.0 × 16384 / 4096 = 4.0g
```

自检屏打出的是 `MPU FS 8g->8g OK`，第 7 行也没有任何 FIX 提示，
**屏幕上全绿**。这是本项目唯一"功能已失效、界面却全部正常"的失效模式，
上一版加的 `! FALL DET DISABLED` 告警行也拦不住它（fatal 恒为 0）。

> **唯一可靠的识破方法**：拿板子静止放平，看 `A:` 行的合加速度。
> 静止时 |a| 物理上必须 ≈1.0g。看到 3.9 / 4.0 就是放大 4 倍，
> 看到 8.0 就是放大 8 倍。这个判据不依赖任何寄存器，寄存器骗不了它。

## 3. 本次改动：两个阈值必须一起抬

阈值在 `user_config.h` 第五节：

| 宏 | 原值 | 现值 | 依据 |
|---|---|---|---|
| `FALL_ACCEL_HIGH_G` | 2.5f | **5.0f** | 必须 > 静止读数 3.9，否则静止就满足条件1、状态机常年卡在 IMPACT |
| `FALL_ACCEL_LOW_G` | 1.5f | **4.5f** | 必须 > 静止读数 3.9，否则条件3 永不成立 |

**只改 HIGH 等于没改。** 这是本次最容易踩的坑：

```
只改 HIGH=5.0, LOW 留 1.5:
  静止      |a| = 3.9  →  3.9 < 5.0   停在 IDLE ✓（看起来好了）
  真摔一次  |a| 冲到 8+ →  进 IMPACT / CONFIRM ✓
  摔后躺地  |a| = 3.9  →  3.9 不小于 1.5 → 条件3 永不满足 → ✗ 不报警
```

关键点：**|a| 是三轴模值，帽子无论朝哪个方向翻，静止时模值恒为 1g**
（放大后恒为 3.9）。所以 LOW 必须抬到 3.9 以上，取 4.5 留 0.6 余量抗噪声。

## 4. 这套值的局限（如实说明，不是标定值）

- `HIGH = 5.0` 相当于真实加速度 `5.0 / 4 = 1.25g`，比需求的 2.5g **灵敏一倍**；
  快步走、弯腰磕碰都可能触发条件1。
- "稳定"窗口只有 4.5~5.0（读数体系），宽 0.5。摔后若还有轻微晃动就会不断
  重置稳定计时，判定可能被拖长或漏掉。
- 结论：**判定能动了，但比原设计敏感且脆弱。** 这是在坏硬件上让它跑起来的
  折中值，不是标定结果。

## 5. 验证方法（烧录后按顺序做）

1. **静止看读数**：`A:` 行应为 `3.9 0.0 0.0` 左右（板子竖直），或按摆放变化，
   但合加速度恒 ≈3.9。若你希望这里显示 1.0，见第 6 节的彻底修法。
2. **轻敲测试**：用手掌快速拍一下帽子（不摔），看是否出现 `FALL ALARM`。
   HIGH=5 相当于 1.25g，**拍一下就可能报** —— 这可能过于灵敏，
   若误报频繁就说明该走第 6 节。
3. **真摔测试**：把帽子从约 1m 高处落到软垫上，应报 `FALL ALARM`
   并蜂鸣 3 秒（`ALARM_FALL`，锁定 10 秒防重复）。
4. 串口（USART2 115200）应同步打印 `[ALARM] fall detected`。

## 6. 更彻底的修法（推荐，但需再改一次）

**既然实际灵敏度是 16384 LSB/g，就按它换算**，让读数回到真实 g：

- 方案 A（改配置，不改代码）：把 `MPU6050_ACCEL_FS_G` 设为 `2`。
  - 效果：读回值也是 2 → `fs_got = 2` → `lsb = 16384` → 静止显示 **1.0g** ✓
  - 附带：`fatal = (2 <= FALL_ACCEL_HIGH_G=5.0) = 1` → 屏幕出现
    `! FALL DET DISABLED` 告警（正确提示：物理量程 2g 确实够不到 5g 阈值）
  - **此时必须把阈值改回 2.5 / 1.5**（读数已是真实 g），屏幕第 7 行会提示
    `FS_G=2 TH 2.5/1.5`。
- 方案 B（不改硬件配置，只改换算）：在 `mpu6050.c` 里加一个"物理灵敏度覆盖"
  宏，强制 `s_accel_lsb_per_g = 16384`，而对上层仍报 `fs_got = 8`。
  - 适合"不想让 `fatal` 亮、也不想动配置"的场景，但会让自检结果与实际不符，
    可读性变差。

**取舍**：
| | 留在放大体系（现状，阈值 5.0/4.5） | 修回真实 g（阈值 2.5/1.5） |
|---|---|---|
| 读数可读性 | 差（静止显示 3.9，别人看不懂） | 好（静止 1.0，符合常识） |
| 判据余量 | 窄（稳定窗口 0.5） | 宽（1.5~2.5，余量 1.0） |
| 冲击上限 | 读数上限 8（= 物理 2g 削顶） | 物理 2g 削顶 |
| 改动量 | 0（已完成） | 1 个宏 + 2 个阈值宏 |

两者的**物理冲击上限是同一个（±2g 削顶）**，差别只在读数是否好看、
阈值窗口是否宽裕。**若追求演示效果和论文可读性，建议走方案 A。**
