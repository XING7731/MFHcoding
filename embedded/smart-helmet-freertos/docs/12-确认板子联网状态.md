# 12 · 确认板子到底连上没有（三种方法 + 四象限判读）

> 本文解决一个问题：**"巴法云显示离线"到底是哪一种离线？**
> 四种原因的处置完全不同，而它们在控制台上看起来一模一样。

---

## 0. 本轮实测结论（2026-09-13 21:40~21:50）

用你的真实私钥实测，得到两条硬结论：

| 实验 | 做法 | 结果 | 说明 |
|---|---|---|---|
| **云端活动采样** | 每 3 秒查一次设备接口, 连续 70 秒 | `time` 一直停在 **21:39:12**（我模拟脚本的时间），纹丝不动 | 这 70 秒内**没有任何新数据**上云 |
| **互踢探测** | 电脑占住私钥连接并订阅，保持 60 秒，每 5 秒发心跳 | `t=0s … t=55s` 心跳**全部正常**，一次没被顶掉 | 巴法云**同私钥只允许一个连接**；若板子在连，它重连时必然把我顶掉。没被顶 ⇒ **板子此刻没有连着巴法云** |
| **电脑完整模拟** | 电脑复刻固件全流程：CONNECT → SUBSCRIBE → 周期 PUBLISH | 订阅后立刻 `online=True`；每轮发布后 `pubOnline=True` 且 `msg` 同步更新 | **代码逻辑、私钥、主题全都没问题** |

**结论：问题不在订阅、不在私钥、不在主题，而在"板子没有成功建链"。**
"离线"只是表象，真正的现象是——**板子现在没有在往巴法云发任何数据**。

> 提醒：此前控制台里 `msg` 一直是 `{"msg":"px"}` 或 `{"msg":"device-sim"}`，
> 那都是**电脑测试脚本**留下的数据，不是你的板子发的。

---

## 1. 四种"离线"，先分清是哪一种

把 `online` / `pubOnline` / `time` 三个字段放在一起看，四种原因立刻分开：

| # | online | pubOnline | 最后数据 time | 含义 | 该做什么 |
|---|---|---|---|---|---|
| ① | false | **false** | 很久以前 / 不动 | **板子根本没连上云端** | 查 AT / WiFi / TCP / MQTT 卡在哪一步（见第 3 节） |
| ② | false | true | **在更新** | 板子连上了、也在发，但**没有订阅** | 固件是旧版（无 SUBSCRIBE）或订阅那步失败 → 重新烧录最新固件 |
| ③ | **true** | true | 在更新 | 一切正常，**控制台其实已在线** | 刷新控制台页面即可 |
| ④ | false | true | 停在很久以前 | 板子**掉线了** | 查供电 / 热点 / 是否被别的连接顶掉 |

**你现在处于第 ① 类。**

---

## 2. 方法一：云端示波器（推荐，不用 OLED、不用 USB-TTL）

```bash
cd tools
python bemfa_watch.py              # 默认 uid/topic，每 3 秒采样一次
```

运行后**去给开发板复位（或重新上电/烧录）**，观察输出：

```
[   0s] 基线  online=False pubOnline=False  最后数据=2026-09-13 21:39:12 (612s前)

  当前判读: ✗ 云端完全没有活动 → 设备【根本没连上】。
```

- 出现 `>>> 检测到【新数据到达】—— 板子正在成功上报！` ⇒ 板子上报成功
- 出现 `>>> online 翻成 True —— 【订阅成功】` ⇒ 在线图标会亮
- **一直毫无变化** ⇒ 板子连链都没建起来，按第 3 节查

常用参数：

```bash
python bemfa_watch.py --interval 2      # 加快采样
python bemfa_watch.py --once            # 只查一次
python bemfa_watch.py --topic helmet001 # 换主题
```

> ⚠ 运行期间**不要**用 MQTTX / mqtt.fx 以同一私钥连接，会把板子顶下线，观察到的就不是板子的状态了。

## 3. 方法二：看板子自己的诊断（OLED 一行 / 串口一行）

固件已经把"建了什么链、卡在哪一步"送到 OLED **最后一行**（第 8 行）：

| OLED 显示 | 卡在哪 | 处置 |
|---|---|---|
| `NET: AT no reply` | **模块完全不理 MCU** | 最优先查：**ESP01S 与 STM32 是否共地**、RX/TX 是否交叉、EN 是否接 3.3V、IO0/IO2 是否悬空、独立电源是否 3.3V |
| `NET: baud=9600` | 模块波特率不是 115200 | 把 `user_config.h` 的 `ESP01S_BAUD_RATE` 改成这个值，重新编译 |
| `NET: WIFI fail` | 连热点失败 | 热点必须 **2.4GHz**；SSID/密码区分大小写；确认热点已开 |
| `NET: TCP fail` | 连不上 `bemfa.com:9501` | 手机热点 DNS 问题 → 固件已支持"域名失败自动改 IP 直连"；或热点本身没通外网 |
| `NET: MQTT rc=XX` | Broker 拒绝 | `rc=05` = 未授权（私钥错）；`rc=04` = 账号密码错。**这两条实测都不该发生**，出现就贴给我 |
| `NET: sub rc=XX` | 连上了但订阅失败 | `rc=80` = 主题不存在/名字写错。**上报不受影响**，只是控制台灰 |
| `NET: retry Ns` | 正在退避重试 | 说明上一轮连接失败，N 是还要等几秒。**这就是"看起来稳定其实没连上"的状态** |
| `NET: OK pub=N` | 一切正常 | 数据在发，N 是已发条数 |

> 想看更详细的六行"病历"：把 `user_config.h` 里 `NET_SELF_TEST` 改成 **1**，重新编译烧录。
> 屏上会显示 `步骤 / resets / 模块最后一句应答 / 波特率 / ovf / err`。
> **其中"模块最后一句应答"是空白，就说明硬件层根本没通。**

## 4. 方法三：电脑扮演 ESP01S 模块（需要 USB-TTL）

把 ESP01S 拔下来，电脑接在 STM32 的 PA9/PA10 上扮演模块（见 `docs/09`）。能跑通 ⇒ 固件没问题、锅在真模块；跑不通 ⇒ 才是固件的事。

---

## 5. 如果第 ① 类一直不消失，按这个顺序查

1. **板子真的在运行吗** —— OLED 亮不亮？按复位有没有反应？
   （如果 OLED 都不亮，先查板子供电，跟网络无关）
2. **ESP01S 与 STM32 是否共地** —— 独立供电时最容易漏的一根线，万用表量 GND 是否导通
3. **ESP01S 的 EN 脚** —— 必须接 3.3V（EN = 老模块的 CH_PD）
4. **IO0 / IO2 必须悬空** —— 任一接地会进下载/SDIO 模式，AT 完全无响应
5. **独立电源是不是 3.3V、电流够不够** —— WiFi 发射峰值约 300mA，VCC-GND 并 100µF
6. **热点** —— 锁 2.4GHz，且能上外网

以上 1~6 全部确认无误，仍然 `AT no reply`，就把 OLED 第 8 行的原文告诉我。

## 6. 工具清单（`tools/` 目录）

| 脚本 | 用途 | 需要什么 |
|---|---|---|
| `bemfa_watch.py` | **云端示波器**：实时盯 online/pubOnline/time，边跑边复位板子 | 只要能上网的电脑 |
| `bemfa_device_sim.py` | 电脑完整复刻固件流程（CONNECT→SUBSCRIBE→PUBLISH），验证云端配置 | 电脑；运行前请把板子断电 |
| `bemfa_online_probe.py` | 三段对比实验：订阅前/订阅保持中/断开后 | 电脑 |
| `esp8266_sim.py` | 电脑扮演 ESP01S 模块，接在 STM32 的 PA9/PA10 上 | USB-TTL |

## 7. 一句话总结

> **订阅 = 在线的开关**（已实测证实）。
> 但你现在连"让云端收到一条数据"都还没做到 —— 所以先别管订阅，
> 先用 `bemfa_watch.py` 确认板子有没有走在联网流程上，再看 OLED 第 8 行告诉卡在哪一步。
