# 09 - 用电脑模拟串口排查（附两个可直接运行的脚本）

> 本文回答：**能不能用电脑"模拟串口"来排查？**
> 能，而且分三个层次，最省事的那个连 USB-TTL 都不需要。

---

## 0. 先看一张分流表

| 你的目的 | 用哪个方案 | 需要什么硬件 |
|---|---|---|
| 验证**私钥 + 主题**对不对（云端配置侧） | ① `bemfa_check.py` | **什么都不需要** |
| 验证 **STM32 固件逻辑**对不对 | ② `esp8266_sim.py` | 一个 USB-TTL 转串口模块 |
| 验证 **ESP01S 模块本体**好不好 | ③ 串口助手手工敲 AT | 一个 USB-TTL 转串口模块 |
| 完全没有硬件，只想跑通协议逻辑 | ④ 虚拟串口对（见第 5 节） | 无（但测不到 STM32） |

排查的原则是**从外往里切**：先把"云端"这一层切掉，再切"模块"，剩下的才是"固件"。
最容易冤枉的是固件 —— 但实际上你这次的故障根本不在固件。

---

## 1. 方案① `bemfa_check.py` —— 电脑直接当设备（零硬件，先做这个）

**思路**：固件要做的事只有三件 —— 连 `bemfa.com:9501`、用私钥作 ClientID 发 MQTT CONNECT、往主题发消息。
这三件事**电脑都能做**，那就不必经过 ESP01S 和 STM32。

```bash
cd tools
python bemfa_check.py --uid <你的私钥> --topic temp001
```

它会依次做 7 步并把结论直接说出来：

1. DNS 解析 `bemfa.com`
2. TCP 握手 9501 端口
3. MQTT CONNECT → 打印 CONNACK 返回码含义
4. SUBSCRIBE 主题 → 打印 SUBACK
5. 分别发布到 `主题` / `主题/set` / `主题/up`，看哪种能收到回环
6. 静听若干秒，看是否有别的设备在往该主题发消息
7. PINGREQ / PINGRESP 心跳

**CONNACK 返回码对照**（脚本会自动翻译）：

| 返回码 | 含义 | 处置 |
|---|---|---|
| `0x00` | 连接被接受 | 私钥没问题 |
| `0x02` | ClientID 被拒绝 | 私钥写错，或该私钥未开通 MQTT |
| `0x04` | 用户名或密码错误 | 方式二 appID/secretKey 填错 |
| `0x05` | 未授权 | 私钥/账号无权限 |
| 收不到 | Broker 无应答 | 多为同私钥已被别的连接占用 |

### 本项目实测结果（2026-09-13）

```
CONNACK 0x00 连接已被接受 —— 私钥可用
SUBACK  0x00 = 订阅成功, 主题 [temp001] 有效
发布到 temp001      -> 本机收到回环
发布到 temp001/set  -> 未回给自己（符合巴法云文档规定）
发布到 temp001/up   -> 未回给自己（符合巴法云文档规定）
心跳正常
```

**结论：私钥和主题都没问题，云端配置这一侧完全排除。**
固件发布到裸主题 `temp001` 是有效做法（巴法云会按标准 MQTT 广播给其他订阅者）。

### 巴法云主题后缀规则（官方文档摘录）

| 发布到 | 行为 |
|---|---|
| `<主题>/set` | 推送给所有订阅该主题的设备（**不推给发布者自己**） |
| `<主题>/up` | 只更新云端数据，不推送 |
| `<主题>`（裸） | 标准 MQTT 广播 |

> 注意：巴法云只支持 QoS 0/1，**用 QoS 2 会被强制下线**，次数多了账号会被限制。

## 2. 方案② `esp8266_sim.py` —— 电脑扮演 ESP01S（推荐，能切出"模块问题"）

**思路**：ESP01S 对 STM32 来说**只是一根串口**。让电脑来扮演它 —— 收到 AT 命令就按 ESP-AT 的格式回话，
并在 `AT+CIPSTART` 时**真的**去连 `bemfa.com:9501`，把 Broker 回来的字节用 `+IPD` 格式转给 STM32。

```
           拔掉 ESP01S
STM32 PA9  ──────────────>  USB-TTL RXD
STM32 PA10 <──────────────  USB-TTL TXD      (USB-TTL 电平跳线选 3.3V)
STM32 GND  <──────────────> USB-TTL GND
```

**关键约束**：

* ESP01S 必须**拔下来 / 断电** —— 否则它和 USB-TTL 同时驱动同一根线，总线冲突
* 电平选 **3.3V**
* PC 会代替 ESP 去连巴法云，**同一个私钥只允许一个连接** → 给其他用同私钥的设备断电

### 运行

```bash
pip install pyserial

python esp8266_sim.py --list          # 先看串口号
python esp8266_sim.py --port COM5     # bridge 模式：真转发到巴法云
```

STM32 那边**一行代码都不用改** —— 对它来说这跟真的 ESP 模块没区别。

### 输出长什么样

```
[MCU->ESP] AT+CWJAP="0001","zxc145236"
[ESP->MCU] 'WIFI CONNECTED'
[ESP->MCU] 'WIFI GOT IP'
[ESP->MCU] 'OK'
[MCU->ESP] AT+CIPSTART="TCP","bemfa.com",9501
[ESP->MCU] 'CONNECT'
[ESP->MCU] 'OK'
[MCU->ESP] CONNECT 报文 46 字节 [10 2c 00 04 4d 51 54 54 04 02 00 3c ...]
[云->ESP] 收到 4 字节 [20 02 01 00]       <-- 巴法云回的 CONNACK，返回码 0x00
[MCU->ESP] PUBLISH 报文 21 字节 [30 15 00 08 74 65 6d 70 30 30 ...]
```

### 怎么判读

| 现象 | 结论 | 下一步 |
|---|---|---|
| STM32 完整跑通，控制台能看到数据 | **固件没问题** | 问题在 ESP01S：优先查供电（独立 3.3V LDO + 100µF），再查接线 |
| 卡在 `AT` 无应答 | 接线/波特率 | 检查 PA9/PA10 是否交叉、共地、波特率 115200 |
| 卡在 `CWJAP` | 与模块无关，是热点问题 | 见 `docs/07` 热点排查 |
| 卡在 `CIPSTART` | PC 网络问题 | PC 能上外网吗？9501 端口被防火墙挡了吗？ |
| 卡在 `CONNACK` | 同私钥被占用 | 给别的板子断电 |

### 故障注入开关（用来验证固件的鲁棒性，不是排障必需）

这些开关能**主动制造故障**，检查固件的重连/退避/自愈逻辑是否按设计工作：

| 开关 | 制造的场景 | 期望固件的行为 |
|---|---|---|
| `--fail-cwjap` | 热点连不上 | 退避重试，日志 `step=2` |
| `--fail-cipstart` | 云端连不上 | 触发 IP 直连回退，日志 `step=4/5` |
| `--fake-dns-fail` | 域名不解析 | 自动改用 `MQTT_BROKER_IP_FALLBACK` 里的 IP |
| `--drop-after 20` | 每 20 条报文掐断一次 | 应能自愈重连，`resets=` 不涨 |

## 3. 方案③ 串口助手手工敲 AT（验证 ESP01S 本体）

接线同上（把 USB-TTL 接到**真的 ESP01S** 上）：

```
ESP01S TX ──> USB-TTL RXD
ESP01S RX <── USB-TTL TXD
ESP01S EN ──> 3.3V          (EN 就是 CH_PD，同脚不同丝印)
ESP01S IO0 / IO2 必须悬空    (接地会进下载模式，AT 无响应)
ESP01S VCC/GND ──> 独立 3.3V，VCC-GND 并 100µF
```

用 SSCOM / XCOM / 任意串口助手，波特率 115200，勾选"发送新行"，逐条敲：

```
AT                        -> OK            (没反应 = 波特率/接线/供电)
AT+GMR                    -> 版本号
AT+CWMODE=1               -> OK
AT+CWJAP="0001","zxc145236"  -> WIFI CONNECTED / WIFI GOT IP / OK   (约 3~8 秒)
AT+CIPSTART="TCP","bemfa.com",9501  -> CONNECT / OK
```

**这一步的意义**：手工都连不上，就**彻底证明**不是 MCU 代码的问题。
手工能连上，但 STM32 连不上 → 回到方案② 对比，差别就在固件或供电。

## 4. `+IPD` 格式说明（脚本已按此实现）

ESP-AT 把下行数据交给 MCU 的格式是：

```
\r\n+IPD,<长度>:<原始字节>
```

例如巴法云回 CONNACK（4 字节）时串口上出现：

```
+IPD,4: 20 02 00 00
```

固件里 `MQTT_Connect()` 用**字节搜索** `0x20 0x02` 定位 CONNACK，不依赖 `+IPD` 前缀对齐，
所以带不带前缀都能正确解析（这点在两个方案里都验证过了）。

## 5. 方案④ 虚拟串口对（com0com / Virtual Serial Port Driver）

**一个常见误解**：装了虚拟串口对，就能让 STM32 连到电脑的虚拟口。

**不行。** 串口是点对点的物理层，虚拟串口对**只在 PC 内部**互联两个软件。
STM32 的 PA9/PA10 是真实的 UART 引脚，必须经过 USB-TTL（或板载 CH340/CP2102）才能进电脑。

虚拟串口对真正有用的场景是：

* 在 **PC 上同时跑**"假 STM32"和"假 ESP"，两个脚本互聊，纯软件验证协议逻辑
* 测试你自己的上位机程序

**如果开发板上没有 USB 转串口芯片**：
STM32F103 自带 USB 外设，理论上可以做成 CDC 虚拟串口，但需要引入 USB 库并大幅改动工程，
排查阶段不推荐 —— 花 5 块钱买个 USB-TTL 更省事。

## 6. 环境准备

两个脚本都只依赖 Python 3 + `pyserial`：

```bash
pip install pyserial
python esp8266_sim.py --list
```

不需要 MQTT 库 —— 报文是手写的（这也是刻意的：不引入第三方依赖，避免"库版本不同导致行为不一致"）。

## 7. 结论（本次实测）

* `bemfa_check.py` 证明：**私钥可用、主题存在、云端链路正常** → 云端配置侧排除
* `esp8266_sim.py` 已用"假 STM32"回放固件的完整 AT 序列自测通过 **20/20**，
  含真连巴法云并取回 CONNACK `0x00`，离线模式与故障注入也全部通过

所以接下来只剩**硬件链路**这一层：**ESP01S 供电 → 接线 → 手机热点**。
按 `docs/07-联网断连排查.md` 的分层表逐项确认即可。
