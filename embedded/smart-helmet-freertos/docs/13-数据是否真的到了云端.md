# 13 · 数据到底有没有真的到云端？—— 用「回环确认」把假成功揪出来

> 现象：板子屏幕上写着 `NET: OK`，`pub` 计数一直在涨，可巴法云控制台上看不到新数据，
> 那一栏 `time` 停在很久以前不动。
>
> 这一篇就是为解决这个问题写的。结论先放在最前面：
> **`AT+CIPSEND` 的 `SEND OK` 只代表「ESP01S 自己的 TCP 栈收下了这串字节」，
> 不代表字节到了巴法云。** 所以 `pub` 涨 ≠ 数据上云。

---

## 一、为什么"发布成功"可能是假的

MQTT QoS0 没有 `PUBACK`。设备把报文交给 TCP，就只能"猜"对方收到了。
而中间隔着一个 ESP01S 模块，多出了一层缓冲：

```
STM32 ──UART──> ESP01S(TCP栈) ──WiFi──> 手机热点 ──公网──> 巴法云
              └─ "SEND OK" 是在这里产生的
```

`SEND OK` 在**第二个箭头之前**就返回了。下面三种情况都会让 STM32 这边一路"成功"，
但巴法云那边什么都收不到：

| # | 情况 | 为什么看不出异常 |
|---|------|------------------|
| ① | **同一私钥被别的客户端顶掉** | 巴法云同一个私钥只允许一条 MQTT 连接。电脑上用 MQTTX / mqtt.fx / 甚至本工程的 `bemfa_check.py`、`bemfa_device_sim.py` 连一次，板子就被踢下线 —— 但模块不一定立刻上报 `CLOSED`，STM32 继续发，继续"成功" |
| ② | **半开连接** | 对端已关闭，模块的 TCP 还没超时，缓冲区照收 |
| ③ | **报文被中间设备丢弃** | 路由器 / 运营商网关掐掉长连接上的数据 |

**共同特征：`pub` 在涨，云端 `time` 不动。** 光看 `pub` 永远分不清是
"云端显示问题"还是"根本没送达"。

---

## 二、判据：让报文自己"回来"

固件订阅的就是上报用的**同一个裸主题**（`temp001`）。巴法云会把消息回推给该主题的
**所有订阅者**，其中就包括设备自己。所以：

1. 每条报文里带一个自增序号：`"seq":123,`
2. 发完之后，在接收缓冲里找 `"seq":123,`
3. **找得到** → 这串字节确实经过了 Broker 又回推回来 ⇒ **真送达**
4. **找不到** → 只是 AT 层的**假成功** ⇒ 云端没收到

> 这个回环机制不是猜的，已用 `tools/bemfa_echo_verify.py` 实测确认：
> 同一连接订阅 + 发布，能收到自己刚发的那条报文，且云端 `msg`/`time` 同步更新。

### 屏幕怎么读

第 8 行（`page 7`）现在会显示：

| 屏幕显示 | 含义 | 该做什么 |
|----------|------|----------|
| `NET: OK p=12 e=12` | p = 发送成功次数，e = **回环确认次数**。两者同步增长 | 一切正常，数据在云端，去控制台看 |
| `NET: p=12 NO ECHO` | 发了 12 次，**一次回环都没收到** | 假成功。看下面第三节 |
| `NET: sub rc=80` | 订阅被拒（主题不存在/无权限） | 数据能上云，但控制台图标是灰的 |
| `NET: retry 20s` | 正在退避重连 | 屏幕上的秒数在变 = 程序活着；长期不动才是真卡住 |

**`p` 涨而 `e` 恒为 0，就是"数据没上去"的确证**，不用再去控制台猜。

---

## 三、`NO ECHO` 了怎么办

### 1) 先排掉头号嫌疑：同一私钥被顶掉

**把电脑上所有用同一个私钥连过云端的程序都关掉**，尤其是：

- MQTTX / mqtt.fx / 各种 MQTT 调试客户端
- 本工程的 `tools/bemfa_check.py`、`tools/bemfa_device_sim.py`、`tools/bemfa_echo_verify.py`
- 浏览器里开着的巴法云 MQTT 控制台（如果你在里面订阅过）
- 旧工程 `stm32-dht11-cloud` 的板子（它用同一个私钥）

然后**给板子断电重启**，让它重新建链。

> 固件已经加了自愈：连续 3 次"发布成功但无回环"（`NET_ECHO_FAIL_MAX`），
> 就判定这条连接是死的，主动断开重连。所以即使被顶掉，90 秒内也会自己恢复。
> 但**源头不断开就永远在和它抢**，所以还是要先把电脑那边的连接关掉。

### 2) 用只读的方式确认（不会踢掉板子）

`tools/bemfa_cloud_monitor.py` 走的是 HTTP 只读接口，**不占用 MQTT 连接、
不会把板子顶下线**，是排查时的首选：

```bash
python tools/bemfa_cloud_monitor.py --seconds 150
```

它会：

- 列出该私钥下的**所有主题**（排除"其实发到了另一个主题"这种可能），
- 然后持续采样 `time` / `msg` / `online` / `pubOnline`，有变化就报警。

判读：

- 某个主题的 `time` 每 ~30s 推一次、`msg` 里是带 `timestamp` / `heart_rate` 的 JSON
  → 板子在正常上报
- 所有主题 `time` 都不动
  → 板子确实没把数据送上去，配合屏幕上的 `NO ECHO` 就是双重确证

### 3) 回环确认失效的兜底

万一哪天巴法云改了行为、不再回推自己发的消息，屏幕上会一直 `NO ECHO`（误报）。
此时把 `user_config.h` 里的开关关掉，改用 HTTP 查询作为唯一判据：

```c
#define NET_ECHO_CONFIRM_ENABLE 0
```

---

## 四、相关配置（`user_config.h`）

```c
#define NET_ECHO_CONFIRM_ENABLE 1     /* 1 = 发布后等待云端回环确认 */
#define NET_ECHO_TIMEOUT_MS     4000  /* 单次等待回环的超时; 巴法云正常 1s 内回 */
#define NET_ECHO_FAIL_MAX       3     /* 连续 3 次无回环 → 判链路已死, 强制重连 */
```

- 关掉回环确认会省掉每次发布后最多 4 秒的等待，但也**重新失去"真假成功"的判别能力**，
  不建议关。
- `NET_ECHO_TIMEOUT_MS` 不建议小于 2000：信号差时回环偶尔会 >1s，
  给太短会把正常的链路误判成假的，导致无谓重连。

---

## 五、串口日志（USART2 115200）里对应的几行

```
[NET] published: {"timestamp":"...","seq":7,...}     ← 发出去的报文, 记下 seq
[NET] echo OK seq=7 e=7                              ← 回环确认成功
[NET] WARN no echo seq=8 (1/3) -> data may NOT have reached cloud
                                                     ← 没等到回环, 计数 1/3
[NET] link is HALF-OPEN (no echo x3) -> force reconnect
                                                     ← 连续 3 次 → 强制重连
```

## 六、一句话总结

> **`pub` 涨不代表数据上云，`e` 涨才代表。**
> 屏幕上 `p` 涨而 `e` 不动 = 假成功，头号原因是同一个私钥被电脑上的调试客户端顶掉了。

---

## 七、判定"是不是别人占着连接"（不用任何仪器，2 分钟）

巴法云同一个私钥只允许一条 MQTT 连接。**要确认是不是别的客户端占着，只需一次
只读查询 + 一次断电**：

1. 电脑上跑（**只用 HTTP 只读接口，不会占连接、不会顶板子**）：
   ```
   python tools/bemfa_cloud_monitor.py --seconds 0
   ```
   它会列出该私钥下**所有主题**的 `online / pubOnline / time / msg`。
2. **把板子断电 30 秒**，再跑一次同样的命令。

| 断电前 | 断电后 | 结论 |
|---|---|---|
| `online = True` | `online = False` | 板子自己就是那个订阅者 ⇒ 板子的连接是活的，问题在"发不出去" |
| `online = True` | **仍然 `True`** | **有别的客户端占着这条连接** ⇒ 板子已被顶下线 |

### 2026-09-13 22:42 的实测快照（板子通电运行中）

```
topic            online    pubOnline  time                 msg
temp001          True      False      2026-09-13 22:11:43  {"seq":8702,"source":"echo_verify"}
```

两处关键信息：

- `time` 停在 **22:11:43**（那是电脑侧验证脚本留下的测试报文），
  到查询时已过去 30 分钟 —— **这段时间云端没有任何新数据**；
- `online=True` 但 `pubOnline=False`：**有订阅者在线上，却没有任何发布者在线**。
  板子明明在 30 秒一发，却完全不计入 —— 说明板子那些"发送成功"根本没到达 Broker。

### 处置顺序（按这个顺序做，别跳）

1. 关掉电脑上**所有**用过这个私钥的东西：MQTTX / mqtt.fx /
   **网页版 MQTT 控制台（浏览器里开着并订阅过主题，也算一个客户端）** /
   本工程 `tools/` 下的 `bemfa_check.py`、`bemfa_device_sim.py`、`bemfa_echo_verify.py`；
2. 确认旧工程 `stm32-dht11-cloud` 的板子没有还在跑（它用的是同一个私钥）；
3. **给板子断电 10 秒再上电**，让它重新建连、重新订阅；
4. 只开着 `tools/bemfa_cloud_monitor.py` 观察：正常时每 30 秒会看到 `time` 推进、
   `msg` 变成板子发的 JSON（带 `"seq"`、`"heart_rate"` 这些字段）。
