## 一、结论速览

1. **"10 次 10 次失败"是我上一轮改动直接造成的，根因是一个 4 倍的口径错误。**
   `max30102.c` 取 FIFO 时写的是 `(v & 0x03FFFF) >> 2` 再存进 `uint16_t` ——
   **18 位原始值被右移 2 位**，所以上报量 `d` 的物理上限是 **65535**，不是 262143。
   docs/36 选 LED 电流时把实测的 `d = 58234` 当成"18 位原始值"去和 262143 比，
   算出"只用了 22%，还有 4 倍余量"。**实际 58234 是右移之后的数，对应 18 位原始值
   232936，已经占满量程 88.9%** —— 早就贴着天花板了。

2. 于是 2.19 倍电流（0x24 → 0x4F）把 18 位原始值推到约 **51 万**，远超 262143 ⇒
   **光电流把 ADC 顶到饱和，波形被削成一条直线** ⇒ 带通之后的交流≈0 ⇒
   一个峰都到不了阈值 ⇒ `s_amp_ref` 恒为 0（屏上 `a=0`、`b=0`）⇒
   每次测量都以 `PPG: no pulse, retry` 结束。**这就是 10/10。**

3. **修法**：LED 电流 `0x4F → 0x20`（15.8mA → 6.4mA），把 `d` 拉回上限的约 79%；
   新增 `PPG_ADC_SAT_LEVEL(65000)` 让屏上直接显示 `ADC SAT d:xxxxx`；
   把 PPG 调试行**上移到** MPU6050 告警之前（此前 `! MPU6050 FAIL` 把 `d/a/b`
   整场测量都盖住了，这是这条故障拖这么久才定位的直接原因）；
   采集窗口 **10 秒 → 15 秒**（有仿真依据，见第六节）。

4. **"先让我有读数"这件事，我没有用"放宽门槛/强行出数"来实现，而且有数据说不该那么做。**
   见第六、七节：低置信兜底给出的值只有 **17%（口径 a）/ 0%（口径 b）**落在 ±5bpm 内；
   自动重试只值 **+4 / 0 个百分点**；自适应早退**比固定窗口更差**。
   读数不是靠开口子捡回来的 —— 而是把 LED 电流这个真因修掉之后会自己回来。

5. **顺带纠正 docs/36 的一个前提**：那条"提高 LED 电流是唯一稳健的杠杆"在仿真模型
   内成立，但**模型没有建 ADC 饱和**，可以任意放大幅度。真机上这个杠杆在 0x24
   （89%）就基本用完了。⇒ 对这套硬件，**幅度这条路是已耗尽的**，
   剩下的唯一可用杠杆是采集窗口长度 —— 正好就是用户问的那件事。

## 二、现场与取证

### 2.1 用户报告

- "我测量 10 次 10 次都失败"（此时固件已是 `PPG_LED_PA_* = 0x4F`）。
- 屏上行 0 恒为 `PPG: no pulse, retry` ⇒ 状态机走到了 DONE，只是没攒够合格拍。
- 用户提供现场截图，第 6 行是 `! MPU6050 FAIL`。

### 2.2 截图里被忽略的一件事

OLED 第 5 行的 PPG 调试行（`d:.. a:.. b:..`）**整场测量都没有出现过** ——
因为显示优先级链是「报警文案 → MPU6050 FAIL → FALL DET DISABLED → ACAL FAIL →
FALL 瞬时态 → PPG 调试行 → STATUS normal」，而 `! MPU6050 FAIL` 是**持续状态**，
把唯一的诊断行永久顶掉了。于是用户只能看到行 0 的 `no pulse, retry` ——
而那一行恰好是"没采到光 / 有光没搏动 / 峰检出但间隔全被拒"三种病因的**共同出口**。

**一个持续存在的告警把诊断行永久遮住，是显示优先级设计上的错。** 已修（见 5.4）。

## 三、真因推导：一个 4 倍的口径错误

### 3.1 驱动里那一行

`user/Src/max30102.c`（FIFO 解码）：

```c
/* 每样本 6 字节: RED 3 字节 + IR 3 字节, 18 位有效 */
v = ((uint32_t)raw[i * 6 + 3] << 16) | ((uint32_t)raw[i * 6 + 4] << 8) | (uint32_t)raw[i * 6 + 5];
f->ir[i] = (uint16_t)((v & 0x03FFFF) >> 2);   /* ← 右移 2 位, 存进 uint16_t */
```

驱动文件头的说明也写了这件事："本驱动把有效位右移 2 位后存入 uint16_t
—— 若你的算法需要完整 18 位分辨率，请改用 uint32_t 缓冲（会显著增加 RAM 占用）"。

**结论：`d`（以及所有进算法的 PPG 样本）的上限是 65535。**
`HR_GetIrDc()` 里的 `clamp_u16` 并没有挡掉任何东西 —— 上游已经限幅了。

### 3.2 把实测值换算回 18 位

| 量 | 值 | 说明 |
|---|---|---|
| 实测 `d`（@0x24, 7.2mA） | 58234 | 这是**右移之后**的数 |
| 对应 18 位原始值 | 58234 × 4 = **232936** | |
| 18 位满量程 | 262143 | |
| **占空比** | **88.9%** | 贴着天花板 |
| `d` 与电流的比例 | 58234 / 36 = **1617.6 counts/LSB** | 饱和前 d ∝ 电流 |

### 3.3 于是 0x4F 必然饱和

0x4F = 79 LSB ⇒ 18 位原始值 ≈ 79 × 1617.6 × 4 ≈ **511,000**，
是满量程 262143 的 **1.95 倍** ⇒ **ADC 恒定输出 262143**。

后果链：

```
光电流过大 → ADC 饱和, 输出恒定 → >>2 之后恒为 65535, 波形是一条直线
  → 带通(高通 0.5Hz + 低通 4Hz)输出 ≈ 0
  → 局部极大值判据 s_v1 > s_v2 && s_v1 >= b_ir && s_v1 > 0 恒不成立
  → on_peak() 一次都不被调用 → s_amp_ref 恒为 0   (屏上 a=0)
  → s_win_ibi 恒为空                              (屏上 b=0)
  → finish_measure(): s_win_ibi_n(0) < PPG_WIN_IBI_MIN(3) → 不给结果
  → HR_ST_DONE + 无效 → 屏上 "PPG: no pulse, retry"
```

**与现场完全吻合：`no pulse, retry`，且频率 10/10。**

### 3.4 为什么当时没能发现（三个叠加的观测盲区）

1. **`d` 顶到 65535 之后"看起来很正常"** —— 因为它离 262143 还很远。
   一个饱和的系统，读数是最"稳"的（纹丝不动），最不像在出问题。
2. **`a=0` 太容易被解释成"指腹没盖住窗口"** —— 那正是 docs/15 第四节的老结论。
   于是线索被导向佩戴，而不是电流。
3. **docs/37 那次改动还在这个方向上加了一把**：把 `d` 报成 uint32，
   并写下"真实直流十几万"的理由 —— 实际上 `d` 的物理上限就是 65535，
   那条理由本身是错的（已在本轮改写，见 `HR_GetIrDcRaw()` 的注释）。

## 四、为什么仿真没能提前拦住

`tools/ppg_yield_sweep.py` 第三节扫过 0x24 / 0x4F / 0x7F / 0xFF 四档，
结论是"都是 100% 出数、0% 错值"，还带了一句注解：

> ⚠ 幅度近似线性只在 LED/ADC 未饱和时成立。d 跟着电流一起涨，
>   18bit ADC 满量程 262143 —— 0xFF(51mA) 会把 DC 顶到 ≈41 万，已经超了。

**这句话里的 262143 是对的，58234 的量纲是错的。** 一句正确的警告 + 一个错的口径
= 结论反向。三个具体问题：

1. **仿真的"幅度"是可以无限放大的一个数**，模型里没有"ADC 会饱和"这件事。
   ⇒ 凡是"把某个模拟量放大 x 倍"就能拿到的收益，都必须先问"真机上这个量能放大到几倍"。
2. **扫描只到 0xFF 才提示超限**，而真机上 0x4F 就已经超了 —— 因为阈值用错了 4 倍。
3. **这正是 docs/36 十二-G 那条教训的另一种形态**：那里是"干扰形态是造假造出来的"，
   这里是"被放大那个量的上限是假的"。**同一类错误：把模型里的可用范围当成了真机的。**

**给下一次的检查单**：任何"某参数往某方向调 → 出数率涨"的结论，必须配一句
"这个方向在真机上能走多远，由哪个读数决定"。本轮那条读数就是 `d`。

## 五、修法

### 5.1 LED 电流：0x4F → 0x20（15.8mA → 6.4mA）

目标 `d` ≈ 0.79 × 65535 ≈ 51763（留 20% 顶部余量给脉搏波峰与中等运动伪影）：

```
51763 / 1617.6 ≈ 32  →  0x20 = 32 × 0.2mA = 6.4mA
预期烧录后: d ≈ 5.2 万, a ≈ 2.8 百(交流比 0x24 时小 11%)
```

**为什么不干脆回到 0x24(7.2mA)**：0x24 时 `d + a = 58234 + 312 = 58546`，
已经是上限的 **89.3%**，只剩 10.7% 余量。指腹贴合松紧、按压力度、隔不隔外壳
都会让直流浮动 10% 以上 —— 贴紧一点就削顶。0x20 把余量从 10.7% 提到 20.9%，
而交流只损失 11%，是"能覆盖佩戴差异"的最小退让。

**由此得到一条硬约束（写进 user_config.h）**：

> `PPG_LED_PA_*` 只能在 `d ≤ PPG_ADC_SAT_LEVEL` 的前提下往上调。
> 每一个 LED 档位都必须**实测一次 `d`** 才能算下一档 ——
> 不能靠"满量程是多少"去推，因为满量程取决于驱动右移了几位。

### 5.2 新增 `PPG_ADC_SAT_LEVEL`（65000）+ 屏显 `ADC SAT`

```c
#define PPG_ADC_SAT_LEVEL     65000.0f
```

取 65000 而不是 65535：FIFO 解出的值本身会在上限附近抖动，距上限不到 1% 就已经是削顶。

OLED 第 5 行新增一条**优先级最高**的分支：

```c
if ((float)HR_GetIrDc() >= PPG_ADC_SAT_LEVEL)
    snprintf(ppgbuf, sizeof(ppgbuf), "ADC SAT d:%u", (unsigned)HR_GetIrDc());
```

理由：屏上一行只有 21 字符，`ADC SAT d:65535` 刚好 15 字符。
而**这一条必须排在 d/a/b 之前**，因为饱和时 `a` 必然是 0 ——
不先排除饱和，`a=0` 一定会被误读成"贴合不好"（这正是上一轮的误判路径）。

### 5.3 采集窗口：10 秒 → 15 秒

依据见第六节。只改了 `PPG_MEASURE_MS`，并同步修正了 `PPG_WIN_MAX` 的注释
（40 拍是按 15000ms / 400ms 不应期算出来的，37 拍上限 + 3 拍余量）——
**以后谁再动 `PPG_MEASURE_MS` 或不应期，都要回来核对 `PPG_WIN_MAX`**，
否则窗口尾部攒到的拍会被静默丢掉（丢的不报错，只让"拍数不够"的失败变多）。

### 5.4 显示优先级：PPG 调试行抢占 MPU6050 告警

```c
/* 原来: MPU6050 异常告警优先, PPG 调试行让位  → d/a/b 永远看不到 */
/* 现在: 只在【正在测量或刚测完且没读出数】时抢占; IDLE 时仍归告警 */
else if (!s.hr_valid && HR_GetState() != HR_ST_IDLE) { ... d/a/b 或 ADC SAT ... }
```

两边都不丢的理由：告警是**持续状态**，什么时候看都能看到；而"这次为什么没测出来"
只在测量那十几秒内可观测。心率一旦读出有效值，`!s.hr_valid` 不成立，
这一行立刻交还给告警。

### 5.5 顺手纠正的注释（都是"错注释比没注释更坏"的实例）

- `heart_rate.c` / `heart_rate.h` 里 `HR_GetIrDcRaw()` 的理由：原写"真实直流十几万
  被 clamp 成 65535" —— **不成立**，已改写为真实情况，并说明它现在只是
  结构性预留（若将来驱动不再右移 2 位，报文不会截断）。
- `heart_rate.c` 文件头新增**追加五**，完整记下这次的根因与上一轮的错误判断。
  **追加四保留不动** —— 它记下了当时的观察（`d` 纹丝不动）与当时的判断，
  对照着看才能看出错在哪一步。

## 六、采集窗口定档：15 秒（以及三条被否掉的改法）

工具：`tools/ppg_retry_sim.py`（输出 `tools/ppg_retry_sim_result.txt`）。
条件取 `ppg_yield_sweep.py` 第十二节那一组（最接近真机）：幅度 305（= 实测 `a` 档）、
噪声 8、漂移 = OU `std=600 tau=0.8s`；**同一组换漂移形态复核一遍**
（不平滑 OU / 带限 OU 1.5Hz），两种实现同方向才算真收益（12-G 的教训）。
每档 3 心率 × 8 realization = 24 组。

### 6.0 先验证方法：离线复算前缀 = 在线逐拍累计

自适应窗口是"在 t 时刻收工"，结果 = 用"入窗时刻 ≤ t 的那些拍"复算中位数。
这与在线逐拍累计**严格等价**，所以不必给状态机再加一条早退分支
（少动一份"可执行规格"）。验证方式：用 10 秒窗口实跑一次、20 秒窗口实跑一次，
比对"20 秒那次的 `win_ibi` 里时刻 ≤ 窗口起点+10 秒的那些拍"是否逐拍
等于"10 秒那次的 `win_ibi`"。

```
共 48 组。边界取 '<= 窗口起点+10s' 时不等价: 4 组
共 48 组。边界取 '<  窗口起点+10s' 时不等价: 0 组
⇒ 采用【开区间】。等价性成立: 离线复算可用。
```

（4 组的差是因为"峰的时刻"取的是检出那一拍的样本时刻，与窗口关闭那一拍
可能有 1 个样本的重叠 —— 是口径差，不是算法差。）

### 6.1 测量时长（窗口长度）

| 档位 | 不平滑 OU<br>出数/错值/无结果 | 带限 OU<br>出数/错值/无结果 |
|---|---|---|
| 固定 **10 秒**（改动前） | 29% / 50% / 21% | 62% / 29% / 8% |
| 固定 **15 秒**（本轮采用） | **42% / 33% / 25%** | **79% / 21% / 0%** |
| 固定 20 秒 | 42% / 42% / 17% | 83% / 17% / 0% |

- **10→15 秒两种漂移同方向且幅度大**（+13 / +17 个百分点）⇒ 经得起复核。
- **15→20 秒收益小、代价高**：等待 +33%；且不平滑那一组错值率从 33% 涨回 42%。
- ⇒ **定 15 秒。**

### 6.2 被否掉之一：自适应窗口（攒够 6~8 拍就提前收工）—— 更差

| 早退规则 | 不平滑 OU 出数率 / 平均窗长 | 带限 OU 出数率 / 平均窗长 |
|---|---|---|
| 门槛过 且 ≥6 拍 | 29% / 12.9 秒 | 67% / 10.4 秒 |
| 门槛过 且 ≥8 拍 | 29% / 14.4 秒 | 62% / 12.8 秒 |
| 门槛过 且 ≥8 拍、一致≥85% | 38% / 17.0 秒 | 67% / 13.9 秒 |
| 门槛过 且 ≥10 拍、一致≥90% | 38% / 18.3 秒 | 75% / 16.0 秒 |
| 对照：固定 15 秒 | **42%** / 15.0 秒 | **79%** / 15.0 秒 |

**在相同甚至更长的平均等待下，出数率一律更低。** 原因：拍数越多，中位数越稳、
"一致占比"越难被系统性双峰伪造；早退等于用"刚好过门槛的那 6 拍"去定结果。
这条最反直觉（直觉是"够了就早点收工"），所以两种漂移都测了。**不做。**

### 6.3 被否掉之二：自动重试（失败就自动重开一个窗口）—— 几乎没用

- 「不平滑」1 次 42% → 2 次 46% → 3 次 50%（错值率同时 33% → 50%）
- 「带限」1 次 79% → 2 次 79% → 3 次 79%（**完全不变**）

机制：带限那组本来就没有"无结果"，而重试**只能把"无结果"变成结果** ——
它救不回已经被判据否掉的错值。而不平滑那组多出来的 4 个百分点，
代价是最长等待翻倍（15→30 秒）。**不做。**

### 6.4 被否掉之三：低置信兜底 —— **不能开**（这是"先让我有读数"的正面回答）

口径：所有尝试都没过高置信门槛时，仍然把窗口内 IBI 的中位数报出来。

| 兜底口径 | 触发组数 | 给出值 | 其中落在 ±5bpm 内 |
|---|---|---|---|
| (a) 拍数 ≥ 3 | 6 / 24 | 6 | **1（17%）** |
| (b) 同意拍数 ≥ 3（保留"至少 3 拍互相一致"，只放弃 70% 占比） | 4 / 24 | 4 | **0（0%）** |
| 带限 OU | 0 / 24 | 0 | 本档没触发 |

- 两种口径的给对率都极低 ⇒ **门槛挡的正是"系统性双峰"，放开就是拿错值换读数。**
- 口径 (b) 比 (a) **更严**、给对率却**更低**（0% vs 17%）——
  说明问题不在"占比门槛"上，而在"这些拍本身就不可信"。**不做。**

> 用户说"先让我有读数"，我没有用"开口子"来兑现。这既与工程一贯的
> "宁可说不知道，也不给错数"一致，也是本轮数据给出的唯一正确选择：
> 读数不是靠放宽门槛捡回来的，而是**把 LED 电流这个真因修掉之后会自己回来**。

## 七、更新后的判读表（屏上第 5 行 + 云端 `d/a/b`）

`d` = 红外直流（上限 **65535**）；`a` = 峰值幅度 `s_amp_ref`；`b` = 窗口内合格 IBI 拍数。

| 屏上 / 报文 | 含义 | 处置 |
|---|---|---|
| `ADC SAT d:655xx` | **ADC 饱和**（光电流过强，波形被削平） | **先降 `PPG_LED_PA_*`**，不要去查佩戴 |
| `d:0` 左右 | 压根没采到光（LED 没亮 / 没盖住光学窗口 / 模块异常） | 查硬件 |
| `d` 正常（几万）、`a:0` | 有光但没有脉搏波，或峰一个都没过阈值 | 查贴合/压力；若 `d` 已近 65000 又要怀疑饱和 |
| `d`、`a` 正常、`b:0` | 峰检出了，但每个间隔都被判据拒掉 | 查运动伪影 / 切迹（docs/32） |
| `d`、`a` 正常、`b` 在涨但最后仍失败 | 攒到了拍，差在"够不够 3 拍 / 一致占比" | 已靠 15 秒窗口改善；再不行才是佩戴 |
| 行尾 `DRP` | FIFO 溢出丢过样本 | 查读取节奏（docs/29）——独立导致心率偏高/抖动 |

**一句话**：`ADC SAT` 这一行是本次新增的，它的存在就是为了让第三节那整条推理链
不再需要人去脑补。
